# PR 리뷰 (수정 금지)

> **구현한 세션과 다른 세션에서 실행하세요.**
> 자기가 쓴 코드를 자기가 승인하면 리뷰가 아닙니다.

## 지시

다음 PR을 **수정하지 말고 리뷰만** 하세요: `{{PR 또는 브랜치}}`

당신의 역할은 **동의하는 것이 아니라 공격하는 것**입니다.
"괜찮아 보입니다"로 끝나는 리뷰는 실패한 리뷰입니다.
문제가 정말 없다면 **어떤 근거로 없다고 판단했는지**를 쓰세요.

## 반드시 실제 코드를 읽을 것

- diff만 보지 말고 **주변 코드와 호출자**까지 읽으세요
- 모든 지적에 **파일 경로 + 라인 번호**를 붙이세요
- 근거 없는 지적은 노이즈입니다

## 중점 검토

### 1. 동시성 정확성
- 읽기-계산-쓰기가 원자적인가, 아니면 원자적 연산을 여러 번 쓰는 것뿐인가
- 락을 잡은 채 느린 작업(네트워크, sleep)을 하지 않는가
- 스레드별 실행 순서를 구체적으로 그려 보고 깨지는 순서가 있는지 찾으세요

### 2. 제한/보호 로직의 정확성
- 제한이 **모든 경로**에 걸리는가 (재시도, 예외 경로, 우회로)
- 경계값에서 어떻게 되는가 (0, 음수, 오버플로)
- 시계를 쓴다면 벽시계인가 단조 시계인가

### 3. 캐시와의 상호작용
- 캐시 hit이 불필요한 대기를 유발하지 않는가
- 캐시가 문제를 **가리고 있지** 않은가
- 캐시를 껐을 때도 정확한가

### 4. 트랜잭션 경계
- 트랜잭션 안에서 외부 시스템을 부르지 않는가
- 같은 빈 안에서 `@Transactional` 메서드를 호출하지 않는가 (프록시를 안 탄다)
- 롤백돼야 할 것과 되면 안 되는 것이 섞여 있지 않은가

### 5. 실패 처리
- 예외를 삼키고 로그만 남기는 곳이 있는가
- 실패했을 때 남는 상태가 **되돌릴 수 있는** 상태인가
- 인터럽트를 삼키지 않는가

### 6. 테스트가 흔들리지 않는가 (flaky)
- `Thread.sleep`으로 타이밍을 맞추고 있지 않은가
- 머신이 느리면 실패하는 단정이 있는가
- **버그가 있어도 통과하는 테스트**는 아닌가 (판별력 확인)
- 테스트가 실제 문제를 검증하는가, 아니면 통과만 시키는가

### 7. 측정의 타당성
- Before/After가 **같은 도구, 같은 조건**으로 측정됐는가
- 측정하는 값이 실제로 주장하는 것을 재고 있는가
- 재지 않은 것을 잰 것처럼 쓰지 않았는가
- 다른 브랜치·다른 시점의 숫자를 섞지 않았는가

### 8. 과한 복잡성
- 이 추상화가 지금 필요한가
- 새 의존성이 정당한가
- **면접에서 5분 안에 설명할 수 있는 구조인가**

### 9. 불필요한 기술 도입
- Redis/Kafka/MQ가 실제 요구사항으로 정당화되는가
- 아니라면 왜 안 넣었는지가 문서에 있는가

### 10. 다중 인스턴스
- 인스턴스가 늘면 깨지는 가정이 있는가
- 그 한계가 문서에 적혀 있는가

### 11. 보안
- 로그·지표·예외 메시지에 비밀값이나 개인정보가 새지 않는가
- 지표 태그 카디널리티가 폭발하지 않는가

## 출력 형식

```
## 심각 (머지 전 반드시 고쳐야 함)
- 파일:라인 — 무엇이 문제이고 어떤 상황에서 깨지는지

## 보통 (고치는 게 좋음)

## 사소 / 취향

## 확인했고 문제없다고 판단한 것
어떤 근거로 그렇게 판단했는지

## 검증하지 못한 것
```

각 지적에 **어떤 입력/상황에서 실제로 깨지는지**를 구체적으로 쓰세요.
"안전하지 않아 보임"이 아니라 "스레드 A가 X 시점에, B가 Y 시점에 들어오면 Z가 된다"로.
