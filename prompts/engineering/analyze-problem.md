# 문제 분석 (수정 금지)

> 이 단계의 목적은 **고치는 것이 아니라 증명하는 것**입니다.
> 코드를 수정하지 마세요.

## 지시

`{{문제 설명}}`

## 반드시 지킬 것

### 1. 실제 코드부터 읽는다
- 추측으로 문장을 쓰지 않는다
- 모든 주장에 **파일 경로 + 라인 번호 + 짧은 코드 인용**을 붙인다
- "~일 것이다", "아마" 같은 표현이 남아 있으면 아직 분석이 끝난 게 아니다

### 2. 흐름을 끝까지 따라간다
- 요청이 들어와서 나갈 때까지의 경로
- 트랜잭션 경계가 어디서 시작하고 끝나는지
- 외부 시스템(DB, S3, 외부 API)을 건드리는 지점
- 캐시·락·재시도가 그 경로의 어디에 있는지

### 3. 실패를 재현한다
- **깨지는 테스트를 만든다.** 통과하는 테스트로는 문제를 증명할 수 없다
- 그 테스트가 **현재 코드에서 실제로 실패하는지 실행해서 확인**한다
- 실패 메시지에 관측된 수치를 담는다 (기대값 vs 실제값)
- 시간·스레드 스케줄에 의존해 흔들리면(flaky) 재현이 아니다. 결정적으로 만든다

### 4. 기존 문서의 숫자를 믿지 않는다
- 문서에 적힌 측정값이 있으면 **지금 코드에서 다시 잰다**
- 재현되지 않으면 그 숫자를 쓰지 말고 **왜 달라졌는지 조사**한다
- 그 사이 코드가 바뀌었을 수 있다

### 5. 고치지 않는다
- 원인을 알아도 이 단계에서는 수정하지 않는다
- 해결책이 떠오르면 메모만 남긴다

## 출력 형식

```
## 현재 구조
파일:라인 + 코드 인용으로 흐름 설명

## 재현
어떤 테스트로, 어떤 조건에서, 어떤 결과가 나왔는지
실제 실행 결과 붙여넣기

## 원인
코드와 실행 순서를 연결해 설명
(동시성이라면 스레드별 타임라인)

## 아직 모르는 것
확인하지 못한 것을 그대로 적는다
```
