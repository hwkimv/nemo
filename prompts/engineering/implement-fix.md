## 지시

`{{재현된 문제}}`

## 반드시 지킬 것

### 1. 대안을 먼저 비교한다
- **최소 3개** 후보를 놓고 **같은 기준**으로 비교한다
- 기준 예: 정확성 / 구현 복잡도 / 의존성 추가 / 테스트 용이성 /
  운영 부담 / 현재 규모에 과한지 / 다중 인스턴스
- 표로 만든다. 서술로 흘리면 비교가 아니다

### 2. 설계 결정은 사람에게 넘긴다
- 추천은 하되 **이유를 명확히** 쓴다
- 이력서 키워드(Redis, Kafka, MSA…) 때문에 기술을 넣지 않는다
- 안 넣은 기술은 **왜 안 넣었는지**, **언제 넣어야 하는지**를 쓴다

### 3. 가장 작은 복잡도를 고른다
- 문제를 제대로 푸는 것 중 가장 단순한 것
- 새 의존성·새 추상화는 그것이 없으면 안 되는 이유가 있을 때만
- "나중에 필요할지도"는 이유가 아니다

### 4. 구현
- 기존 코드 스타일을 따른다
- **왜 이렇게 했는지**를 주석에 남긴다. 무엇을 하는지는 코드가 이미 말한다
- 특히 **하지 않기로 한 것**과 그 이유를 남긴다

### 5. 검증
- 재현 테스트가 **실패 → 통과**로 바뀌는지 확인
- 그 테스트가 **수정 전 코드에서는 여전히 실패하는지** 확인
  (통과해 버리면 판별력이 없는 테스트다)
- 경계·실패 경로 테스트를 추가한다
- **전체 테스트를 돌린다**

### 6. 측정
- Before/After를 **같은 도구, 같은 조건**으로 잰다
- 측정 자체를 재실행 가능하게 만든다 (스크립트나 태스크)
- 재지 않은 것은 "재지 않았다"고 쓴다. 추정치를 측정치처럼 쓰지 않는다
- trade-off를 구분한다: 좋아진 것 / 대가로 잃은 것

### 7. 셀프 리뷰
구현이 끝나면 자기 코드를 공격한다. **최소 1건은 찾는다.**
- 방금 고친 문제가 남아 있는 다른 경로는 없는가
- 실패 경로를 빠뜨리지 않았는가
- 테스트가 시간에 의존해 흔들리지 않는가
- 측정이 실제로 그걸 재고 있는가

```
## Trade-off

## 셀프 리뷰에서 찾은 것
```
