# 지도 API 로컬 캐시 효과 측정

**상태:** Verified

**측정일:** 2026-08-14

**대상:** `NaverApiClient`의 `ConcurrentHashMap` + TTL 2분 로컬 캐시

> ⚠️ **정직성 메모** — 이 캐시는 **Caffeine도 Redis도 아닙니다.**
> `ConcurrentHashMap`에 응답과 저장 시각을 담아두고 읽을 때 나이를 재는 방식입니다.
> 문서에 Caffeine/Redis 경험으로 쓰지 않습니다.

---

## 1. 30초 요약

같은 뷰포트를 반복 조회할 때:

| 지표 | 캐시 OFF | 캐시 ON |
|---|---:|---:|
| 외부 API 호출 (20회 요청) | **820회** | **0회** |
| 응답 avg | **8,202ms** | **8.3ms** |
| 응답 p95 | 8,218ms | 12.6ms |

첫 조회(cold)는 캐시가 있어도 **7,321ms**가 걸립니다. 캐시는 **반복을 없애는 것이지 첫 요청을 빠르게 만들지 않습니다.**

측정 중 발견한 것도 함께 적습니다.

- 뷰포트 **1회 요청이 외부 API를 41번** 부릅니다. 이게 근본 문제입니다.
- 응답시간의 대부분은 네트워크가 아니라 **코드에 하드코딩된 레이트 리미터**(호출 간 200ms)입니다.
- 검색 키워드 목록에 **중복이 있고, 캐시가 그것을 가려주고 있었습니다.**

## 2. 캐시 구조 (코드 기준)

`backend/src/main/java/com/nemo/backend/domain/map/util/NaverApiClient.java`

| 항목 | 값 |
|---|---|
| 자료구조 | `ConcurrentHashMap<String, CacheEntry>` |
| key | **완성된 요청 URI 문자열** |
| value | 응답 body(`Map`) + 저장 시각(`savedAtMs`) |
| TTL | 기본 **120초** (`naver.cache.ttl-seconds`, 0이면 비활성) |
| 공유 범위 | Local Search와 Reverse Geocode가 **같은 Map**을 사용 |
| 크기 제한 | **없음** |
| 만료 정리 | **읽을 때만.** 다시 읽히지 않는 항목은 계속 남음 |

### hit / miss 흐름

```
searchLocal(query, display, start, sort)
  │
  ├─ URI 조립 → 이게 곧 cache key
  ├─ loadFromCache(key)
  │    ├─ TTL 0        → null (캐시 비활성)
  │    ├─ 항목 없음     → null                        ── MISS
  │    ├─ 나이 ≤ TTL   → 저장된 body 반환             ── HIT (외부 호출 없음)
  │    └─ 나이 > TTL   → remove 후 null               ── MISS (만료)
  │
  ├─ (MISS인 경우) enforceMinInterval() — 직전 외부 호출로부터 200ms 대기
  ├─ RestTemplate.exchange(...)  ← 실제 외부 호출
  └─ saveToCache(key, body)
```

**key가 URI 전체라는 점이 중요합니다.** `query`·`display`·`start`·`sort` 중 하나만 달라도 다른 항목이 됩니다.

## 3. 측정 환경

실제 네이버 API를 쓰면 호출 횟수를 셀 수 없고 쿼터·요금·응답 변동이 측정을 오염시킵니다.
그래서 같은 자리에 **호출 수를 세는 스텁**을 두었습니다.

| 항목 | 값 |
|---|---|
| 스텁 | `tools/performance/naver-stub/stub.py` (`--latency-ms 50`) |
| 앱 | dev 프로필(H2). 지도 경로는 DB를 거의 쓰지 않음 |
| 요청 | `GET /api/map/photobooths/viewport` — 강남구 역삼동 부근 뷰포트 |
| 반복 | 워밍업 1회 후 동일 요청 20회 |
| 캐시 전환 | `NAVER_CACHE_TTL_SECONDS=0` (OFF) / `=120` (ON) — **같은 빌드** |

```bash
python3 tools/performance/naver-stub/stub.py --port 9999 --latency-ms 50 &

NAVER_OPENAPI_LOCAL_ENDPOINT=http://localhost:9999/v1/search/local.json \
NAVER_OPENAPI_REVERSE_ENDPOINT=http://localhost:9999/map-reversegeocode/v2/gc \
NAVER_CACHE_TTL_SECONDS=0 ./gradlew bootRun      # OFF
```

호출 수는 `curl http://localhost:9999/__stats`로 읽고 `POST /__reset`으로 초기화합니다.

## 4. 뷰포트 1회 요청의 외부 호출 수

캐시를 끈 상태에서 **딱 한 번** 요청했을 때:

```
{"local": 40, "reverse": 1, "total": 41}
```

내역:

```
  1  Reverse Geocode        중심 좌표 → "강남구 역삼동"
 40  Local Search           키워드 10개 × 최대 4페이지
────
 41
```

키워드 10개는 `KEYWORDS` 9개(`포토부스`, `인생네컷`, `하루필름` …)에 보조 키워드 1개를 더한 것이고,
각 키워드마다 `MAX_PAGES_PER_KEYWORD = 4`까지 페이지를 넘깁니다.

**응답시간의 정체** — 41회 × 200ms = 8,200ms.
측정된 avg 8,202ms와 정확히 일치합니다. 스텁의 50ms 지연은 200ms 간격 안에 묻힙니다.

즉 이 API가 느린 이유는 네트워크가 아니라 **`MIN_INTERVAL_MS = 200`이라는 하드코딩된 레이트 리미터**입니다.

## 5. 캐시 OFF / ON 비교

### 반복 요청 20회

| | 캐시 OFF | 캐시 ON |
|---|---:|---:|
| 외부 호출 | **820회** (41 × 20) | **0회** |
| avg | **8,202.4ms** | **8.3ms** |
| p95 | 8,217.9ms | 12.6ms |
| min | 8,141.1ms | 4.9ms |
| max | 8,219.2ms | 17.0ms |

### 첫 조회(cold)는 캐시가 있어도 느리다

| | 시간 | 외부 호출 |
|---|---:|---:|
| cold (캐시 ON, 첫 요청) | **7,320.7ms** | 37 |
| warm (이후 20회) | 8.3ms | 0 |

**캐시는 반복을 없앨 뿐 첫 요청을 빠르게 만들지 않습니다.**
사용자가 처음 지도를 열면 여전히 7초를 기다립니다. 이건 캐시로 풀 문제가 아니라 **호출 수 자체를 줄여야 하는 문제**입니다.

### cold가 41이 아니라 37인 이유 — 측정 중 발견한 버그

캐시 ON의 cold 요청은 41회가 아니라 **37회**였습니다. 4회가 사라졌습니다.

```java
for (String base : KEYWORDS) {          // KEYWORDS[0] == "포토부스"
    searchKeywords.add(regionName + " " + base);
}
searchKeywords.add(regionName + " 포토부스");   // ← 같은 키워드를 한 번 더
```

`"강남구 역삼동 포토부스"`가 **두 번** 만들어집니다. 페이지 4개 × 중복 1개 = 4회.
캐시가 켜져 있으면 두 번째 키워드는 전부 hit이라 외부 호출이 4회 줄어듭니다.

**캐시가 코드의 중복을 가려주고 있었습니다.** 캐시를 끄자 드러났습니다.

## 6. TTL 만료 동작

HTTP 레벨에서 2분을 기다리는 대신, 저장 시각을 과거로 밀어 만료를 만드는 단위 테스트로 확인했습니다.
(`NaverApiCacheTest`)

| 확인 | 결과 |
|---|---|
| 같은 검색 10회 반복 | 외부 호출 **1회** |
| 캐시 OFF에서 10회 | 외부 호출 **10회**, 캐시 항목 **0개** |
| 파라미터 하나만 달라진 요청 | 각각 별도 항목 (URI 전체가 key) |
| TTL 경과 후 재조회 | 다시 외부 호출 (**2회**) |
| 만료 후 다시 읽지 않은 항목 | **그대로 남음** (읽을 때만 정리) |

만료 직후 요청은 결국 cold와 같은 비용을 냅니다. **2분마다 한 번은 7초를 내는 구조**입니다.

## 7. 한계

### stale data

TTL 2분 동안은 옛 응답을 돌려줍니다. 포토부스 정보는 분 단위로 바뀌지 않으므로 현재 도메인에서는 감수할 만합니다.
다만 **폐업한 매장이 최대 2분간 지도에 남습니다.**

### 메모리 — 상한이 없다

`ConcurrentHashMap`에 크기 제한이 없고, 만료 정리는 **읽을 때만** 일어납니다.
다시 조회되지 않는 항목은 TTL이 지나도 남습니다.

증가 경로가 두 가지인데 성질이 다릅니다.

| key | 증가 요인 | 위험 |
|---|---|---|
| Local Search | 지역명 × 키워드 10 × 페이지 4 | 지역 단위라 **재사용이 잘 됨** |
| Reverse Geocode | **좌표 그 자체** | 지도를 1m만 움직여도 새 key |

실제로 서로 다른 뷰포트 3곳을 조회했을 때 Local Search는 **0회**(같은 지역이라 전부 hit),
Reverse Geocode는 좌표가 달라 매번 새 항목이 됐습니다.

서울의 행정동만 약 467개입니다. Local Search만 해도 467 × 40 = **약 18,700개 항목**이 쌓일 수 있고,
Reverse Geocode는 사용자가 지도를 움직이는 만큼 **무한히** 늘어납니다.

→ 개선 방향: 좌표를 소수점 3자리(약 100m)로 반올림해 key를 만들면 증가가 멈춥니다.
→ 크기 상한과 LRU 축출이 필요합니다. **Caffeine을 도입한다면 바로 이 이유** 때문입니다.

### 다중 인스턴스

인스턴스마다 별도 Map입니다. 서버가 2대면 캐시도 2벌이고, 같은 지역 첫 요청을 **각각** 겪습니다.
재시작하면 전부 사라집니다.

```text
Instance A ─ (자기 Map)
Instance B ─ (자기 Map)   ← 같은 지역을 각자 다시 채운다
```

**지금은 단일 인스턴스라 문제가 되지 않습니다.** 인스턴스를 늘릴 때 Redis를 검토할 근거가 여기입니다.

## 8. 결론

**캐시는 제 역할을 하고 있습니다.** 반복 조회에서 외부 호출을 완전히 없앴고 응답을 8.2초 → 8.3ms로 줄였습니다.

**그런데 캐시가 진짜 문제를 가리고 있습니다.**

1. 뷰포트 1회에 외부 API를 **41번** 부르는 구조
2. 그중 4번은 **중복 키워드**
3. 응답시간의 실체는 **200ms 하드코딩 레이트 리미터**

우선순위는 Redis 도입이 아니라 **호출 수 자체를 줄이는 것**입니다.

| 우선순위 | 할 일 | 기대 |
|---|---|---|
| 1 | 중복 키워드 제거 (`distinct`) | 41 → 37회 |
| 2 | 키워드·페이지 수 재검토 (정말 10×4가 필요한가) | 대폭 감소 가능 |
| 3 | 좌표 반올림으로 Reverse Geocode key 안정화 | 메모리 무한 증가 차단 |
| 4 | 캐시 크기 상한 + LRU | Caffeine 도입 근거 |
| 5 | 다중 인스턴스가 될 때 Redis | 지금은 근거 없음 |

## 9. 재현

```bash
# 1) 스텁 실행
python3 tools/performance/naver-stub/stub.py --port 9999 --latency-ms 50 &

# 2) 캐시 OFF로 앱 실행
cd backend && SPRING_PROFILES_ACTIVE=dev \
  NAVER_LOCAL_CLIENT_ID=stub NAVER_LOCAL_CLIENT_SECRET=stub \
  NAVER_MAP_CLIENT_ID=stub NAVER_MAP_CLIENT_SECRET=stub \
  NAVER_OPENAPI_LOCAL_ENDPOINT=http://localhost:9999/v1/search/local.json \
  NAVER_OPENAPI_REVERSE_ENDPOINT=http://localhost:9999/map-reversegeocode/v2/gc \
  NAVER_CACHE_TTL_SECONDS=0 APP_S3_CREATEBUCKETIFMISSING=false ./gradlew bootRun

# 3) 토큰 발급 후 동일 뷰포트 반복 요청
curl -s -X POST "http://localhost:8080/api/auth/dev/seed?email=map@nemo.test"
curl -s -X POST http://localhost:9999/__reset
curl -H "Authorization: Bearer <token>" \
  "http://localhost:8080/api/map/photobooths/viewport?neLat=37.5030&neLng=127.0450&swLat=37.4930&swLng=127.0350"
curl -s http://localhost:9999/__stats

# 4) NAVER_CACHE_TTL_SECONDS=120 으로 다시 실행해 비교
```
