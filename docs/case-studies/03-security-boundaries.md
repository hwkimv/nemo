# Case Study — 인증·권한 경계의 구멍 4개 막기

> **한 줄 요약** — 남의 사진을 내 앨범에 넣을 수 있었고, 모든 사용자의 Access Token이 서버 로그에 남고 있었습니다. 재현 테스트를 먼저 만들고 4건을 각각 독립 커밋으로 고쳤습니다.

| | |
|---|---|
| **기간** | 2026-08-14 |
| **범위** | Backend (Spring Boot) — auth · album · security |
| **결과** | 회귀 테스트 17개 추가, 전체 테스트 통과 |
| **증거** | 테스트 코드, 커밋 4개 |

---

## Problem

성능 개선을 하려고 코드를 읽다가, 성능보다 먼저 처리해야 할 것들을 발견했습니다.

| ID | 문제 | 사용자 영향 |
|---|---|---|
| P0-1 | 모든 `/api/**` 요청의 `Authorization` 헤더가 INFO 로그에 기록됨 | 로그가 새면 토큰 만료 전까지 계정 도용 가능 |
| P0-2 | **다른 사용자의 사진을 내 앨범에 넣을 수 있음** | 타인 사진 노출 |
| P0-3 | 토큰 재발급의 DB 쓰기가 유실될 수 있음 | 재발급 직후 로그아웃되는 현상 |
| P0-4 | 토큰이 만료된 사용자는 로그아웃 불가 | 로그아웃이 가장 필요한 순간에 실패 |

집에 물이 새는데 신발장부터 정리할 이유는 없다고 판단해, 측정까지 끝난 N+1보다 이쪽을 먼저 처리했습니다.

---

## Analyze / Constraints

**P0-2가 가장 위험했습니다.** 권한 검사 코드가 이미 있었는데도 뚫린 경우이기 때문입니다.

```java
List<Photo> photos = photoRepository.findAllById(req.getPhotoIdList());
```

`findAllById`는 "이 ID들을 가져와"일 뿐 소유자를 묻지 않습니다.
기존 `canManagePhotos()`는 **"이 앨범을 수정할 수 있는가"** 만 검사합니다.
**"이 사진을 사용할 수 있는가"** 는 다른 질문인데 아무도 묻지 않았습니다.

> 냉장고를 열 권한이 있다고 해서 남의 반찬을 넣을 권한이 생기지는 않습니다.

**제약** — 각 문제를 한 커밋에 섞지 않기로 했습니다. 보안 수정은 나중에 되짚을 일이 많고, 무엇이 왜 바뀌었는지 커밋 단위로 남아야 합니다.

---

## Options

**P0-2의 정책을 먼저 정해야 했습니다.** 코드가 정책을 우연히 결정하게 두면 안 되기 때문입니다.

| 정책 | 장점 | 위험 |
|---|---|---|
| 요청자 소유 사진만 허용 | 단순, 안전 | 공유 앨범 편집자가 불편할 수 있음 |
| 공유 앨범 편집자에게 앨범 주인 사진 허용 | 유연 | 어떤 사진이 어디까지 퍼지는지 추적이 어려워짐 |

**첫 번째를 골랐습니다.** 넓히는 것은 나중에 명시적으로 할 수 있지만, 이미 새어나간 뒤에 좁히는 것은 늦습니다.

**P0-3은 원인을 확정하기 어려웠습니다.** `@Transactional(readOnly = true)`가 붙은 메서드가 DB에 쓰고 있었는데, 코드만 보고 "항상 실패한다"고 단정할 수 없었습니다. 그래서 **어노테이션을 되돌려 테스트가 실제로 깨지는지 확인**한 뒤에 원인으로 확정했습니다.

---

## Action

각 문제마다 **실패를 재현하는 테스트를 먼저** 만들고 고쳤습니다.

### P0-1 — 토큰 로그 제거 + 추적 수단 확보

토큰 로그를 지우면 "어느 요청이 문제였는지" 찾을 방법이 없어집니다. 그래서 대체 수단을 함께 넣었습니다.

- `Authorization` 로그 완전 삭제 (앞 몇 글자도 남기지 않음)
- 남기는 값은 비밀이 아닌 것만: method, URI, status, 처리시간
- `RequestIdFilter` 추가 — 요청마다 ID를 부여해 **그 요청의 모든 로그에 같은 ID**가 찍히고, 응답 헤더 `X-Request-Id`로도 반환

```
INFO [a3f9c1d2] [REQ] GET /api/albums status=200 42ms
```

→ "앱에서 오류가 났다"는 제보를 받으면 그 ID로 해당 요청만 정확히 추적할 수 있습니다.

### P0-2 — 사진 소유권 검증

```java
// 조회 조건 자체에 소유자를 넣어, 남의 사진은 애초에 결과에 나오지 않게 한다
List<Photo> findAllByIdInAndUserIdAndDeletedIsFalse(Collection<Long> ids, Long userId);
```

- 중복 제거한 요청 개수와 조회 결과 개수를 비교해, **하나라도 사용 불가면 요청 전체를 실패**시킵니다.
  일부만 조용히 추가하면 사용자는 무엇이 빠졌는지 모르고, 공격자에게는 "어떤 ID가 통과하는지" 알려주는 신호가 됩니다.
- `photoIdList`뿐 아니라 **`coverPhotoId` 경로**에도 같은 정책을 적용했습니다. 커버는 별도 코드 경로라 목록만 막으면 그대로 우회됩니다.
- 없음 / 삭제됨 / 남의 것을 **`PHOTO_NOT_USABLE` 하나**로 합쳐 응답합니다. 구분해 알려주면 어떤 ID가 실재하는지 탐색하는 통로가 됩니다.

### P0-3 — 트랜잭션 두 겹의 문제

`readOnly = true`를 떼는 것만으로는 부족했습니다. 만료 토큰 처리가 이런 구조였습니다.

```java
delete(stored);                        // 지우고
throw new ApiException(INVALID_TOKEN); // 예외 → 롤백 → 삭제도 되돌아감
```

**"요청은 실패시킨다"와 "쓸모없어진 데이터는 치운다"는 서로 독립적인 작업**입니다.
그래서 삭제만 `REQUIRES_NEW`로 분리했습니다. self-invocation은 프록시를 타지 않으므로 별도 빈으로 뒀습니다.

### P0-4 — 공개 경로 목록 통합

실제 endpoint는 `/api/users/logout`인데 보안 설정 두 곳에는 **존재하지 않는** `/api/auth/logout`이 들어 있었습니다.
원인은 **같은 목록을 두 파일이 각자 들고 있었던 것**입니다.

`PublicEndpoints` 한 곳으로 모아 두 곳이 같은 목록을 참조하게 했습니다. 한쪽만 고쳐서 어긋나는 일이 구조적으로 불가능해집니다. `/api/users/**` 전체를 열지 않고 로그아웃 경로 하나만 열었습니다.

## Result

| 검증 | 테스트 | 확인 내용 |
|---|---:|---|
| 토큰 로그 | `RequestLoggingSecretsTest` (3) | 토큰 원문·앞 16글자·`Bearer` 어느 것도 로그에 없고, method·URI·status는 남음 |
| 사진 소유권 | `AlbumPhotoOwnershipTest` (7) | 사용자 A·B를 실제로 만들어 생성·추가·cover 경로 각각 재현. 섞어 보낸 요청은 **부분 성공 없이 전체 실패** |
| 토큰 재발급 | `AuthServiceRefreshTransactionTest` (3) | 트랜잭션 밖에서 DB를 다시 읽어 삭제·회전이 커밋됐는지 확인 |
| 로그아웃 경로 | `LogoutEndpointSecurityTest` (4) | 만료 토큰으로 로그아웃 성공, `GET /api/users/me`는 **여전히 401** |

**P0-3의 원인은 추측이 아니라 재현된 사실입니다.** `@Transactional`을 다시 `readOnly = true`로 되돌리고 테스트를 돌리자 회전 테스트가 실패했고, 확인 후 수정본으로 복원했습니다.

---

## Limit / Next Condition

- **`AuthServiceRefreshTransactionTest`는 H2에서 돕니다.** flush 유실은 Hibernate 레벨 동작이라 H2로도 재현되지만, 운영 PostgreSQL 동작까지 증명한 것은 아닙니다.
- **QR payload와 소셜 로그인 provider token은 아직 점검하지 않았습니다.** 토큰 로그와 같은 기준을 적용해야 합니다.
- **사진 소유권 정책은 가장 좁게 잡았습니다.** 공유 앨범 편집 요구가 실제로 생기면 그때 명시적으로 넓힙니다.
