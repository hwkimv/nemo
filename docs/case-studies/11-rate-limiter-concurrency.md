# Case Study — AtomicLong을 썼는데 동시 요청에서 전혀 막지 못한 레이트 리미터

> **한 줄 요약** — 외부 API 호출을 초당 5회로 묶으려던 리미터가 **동시 요청에서는 아무것도 막지 않고 있었습니다.** 동시 16건에서 **74.0 req/s**(목표의 14.8배)를 실측했습니다. `AtomicLong`을 쓰고 있었지만 `읽기 → 계산 → sleep → 쓰기` 전체가 원자적이지 않았습니다. CAS 슬롯 예약으로 고쳐 **모든 동시성에서 정확히 5.0 req/s**가 됐습니다.

| | |
|---|---|
| **기간** | 2026-08-21 |
| **범위** | Backend — `NaverApiClient` 외부 호출 속도 제한 |
| **결과** | 동시 16건 **74.0 → 5.0 req/s** (기존 설정값 기준 목표 5.0) |
| **증거** | `NaverApiRateLimitTest` (12), `rateLimitMeasurement` 태스크 |
| **추가 의존성** | **없음** |

---

## Problem

[CS 06](06-monitoring.md)에서 지표를 붙이다가 발견한 문제입니다.
그 문서에는 이렇게 적혀 있었습니다.

> 동시 8건 → **40.2회/초** (의도 5회/초)

**고치지 않고 남겨 뒀습니다.** "지표가 문제를 찾아줬다"는 인과를 흐리지 않으려고
그때는 발견만 기록했습니다. 이번에 그걸 처리했습니다.

## 발견 과정 — 기존 숫자를 그대로 쓰지 않았다

먼저 **40.2가 지금도 재현되는지** 확인했습니다. 재현되지 않았습니다.

원인은 그 사이 코드가 바뀐 것이었습니다.

| | 측정 당시 (2026-08-14) | 지금 |
|---|---|---|
| 뷰포트 1회의 외부 호출 수 | **41회** | **10회** |
| 8건 × 호출 수 ÷ 벽시계 | 328 ÷ 8.2s = 40.2 | 계산 자체가 성립 안 함 |

[PR #12](05-map-api-cache.md)에서 페이지 루프를 없애며 41 → 10으로 줄었기 때문입니다.
**측정 대상이 달라졌으므로 옛 숫자를 그대로 쓸 수 없습니다.**

대신 **리미터를 직접 때리는 측정 도구**를 만들었습니다.
뷰포트를 거치면 캐시·키워드 수 같은 변수가 끼어 리미터만 보기 어렵습니다.

## 재현

`RateLimitMeasurementTest` — 스레드 n개가 각각 10회씩 외부 호출을 시도하고,
**실제로 나간 호출의 시각**을 기록합니다.

```bash

```

### 수정 전

| 동시성 | 총 호출 | 지속 | **관측 rps** | 목표 | 평균 간격 | **최소 간격** | 실패 |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 1 | 10 | 1,909ms | 4.8 | 5.0 | 209.0ms | 200ms | 0 |
| 4 | 40 | 2,103ms | **18.6** | 5.0 | 53.9ms | **0ms** | 0 |
| 8 | 80 | 2,126ms | **37.2** | 5.0 | 26.9ms | **0ms** | 0 |
| 16 | 160 | 2,149ms | **74.0** | 5.0 | 13.5ms | **0ms** | 0 |

**단일 스레드에서는 정확히 동작합니다.** 그래서 지금까지 아무도 몰랐습니다.
동시 요청이 들어오는 순간 호출률이 **동시성에 정비례**합니다.

호출 간격을 그대로 보면 무슨 일이 일어나는지 보입니다. 동시 16건:

```

```

**딱 한 번 199ms를 자고, 나머지 14건이 거의 동시에 나갑니다.**

## 원인

문제의 코드는 세 줄입니다. (`NaverApiClient.enforceMinInterval()`, 수정 전)

```java
private void enforceMinInterval() {
    long now = System.currentTimeMillis();
    long last = lastCallAt.get();                    // ① 읽고
    long elapsed = now - last;
    if (elapsed < MIN_INTERVAL_MS) {
        sleepSilently(MIN_INTERVAL_MS - elapsed);    // ② 자고
    }
    lastCallAt.set(System.currentTimeMillis());      // ③ 쓴다
}
```

`AtomicLong`을 쓰고 있습니다. 그래서 안전해 보입니다.
하지만 **`get()`과 `set()`이 각각 원자적일 뿐, ①②③ 전체는 하나의 원자적 연산이 아닙니다.**

### 스레드 실행 순서

```
시각    스레드 A                     스레드 B                     스레드 C
────────────────────────────────────────────────────────────────────────
t=0     ① last = 1000 읽음
t=0                                  ① last = 1000 읽음           ① last = 1000 읽음
        (셋 다 같은 값을 읽는다)
t=0     ② 200ms 대기 계산            ② 200ms 대기 계산            ② 200ms 대기 계산
        (셋 다 같은 대기 시간)
t=200   ② sleep 끝                   ② sleep 끝                   ② sleep 끝
t=200   ▶ 외부 API 호출              ▶ 외부 API 호출              ▶ 외부 API 호출
        ★ 세 건이 거의 동시에 나간다
t=200   ③ set(1200)                  ③ set(1200)                  ③ set(1200)
        (덮어쓰기. 순서도 의미 없다)
```

핵심은 **①에서 읽은 값이 ③에서 쓰기 전까지 다른 스레드에게 그대로 보인다**는 것입니다.
n개 스레드가 같은 값을 읽으면 **모두 같은 시각에 깨어나** 함께 나갑니다.

그래서 실질적인 제한이 `5 × n회/초`가 됩니다.
측정값이 정확히 그 모양입니다 — 4 → 18.6, 8 → 37.2, 16 → 74.0.

### 두 번째 결함 (셀프 리뷰에서 발견)

`enforceMinInterval()`이 **429 재시도 루프 밖**에 있었습니다.

```java
enforceMinInterval();                         // ← 한 번만
for (int attempt = 1; attempt <= 3; attempt++) {
    restTemplate.exchange(...);               // ← 최대 3번 호출
```

한 번의 `searchLocal()`이 **차례는 1개만 잡고 외부 호출은 최대 3번** 할 수 있었습니다.
429를 받고 재시도하는 상황은 이미 네이버가 "너무 많다"고 말한 상태입니다.
**그때야말로 간격을 지켜야 합니다.**

## AI가 제시한 대안

여섯 가지를 같은 기준으로 비교했습니다.

| # | 방식 | 동시성 안전 | 복잡도 | sleep 중 락 점유 | burst | timeout | 테스트 용이성 | 의존성 | 다중 인스턴스 | 현재 규모에 과한가 |
|---|---|---|---|---|---|---|---|---|---|---|
| 1 | `synchronized` | ✅ | 최소 | **점유함** | ❌ | ❌ 불가 | 쉬움 | 없음 | ❌ | 아니오 |
| 2 | `ReentrantLock` | ✅ | 낮음 | 점유함 | ❌ | ✅ | 쉬움 | 없음 | ❌ | 아니오 |
| 3 | **CAS 슬롯 예약** | ✅ | 낮음 | **점유 안 함** | ❌ | ✅ | 쉬움 | **없음** | ❌ | 아니오 |
| 4 | Resilience4j | ✅ | 중간 | 안 함 | 설정 | ✅ 내장 | 보통 | **추가** | ❌ | **다소** |
| 5 | Bucket4j | ✅ | 중간 | 안 함 | ✅ | ✅ | 보통 | **추가** | 별도 | **다소** |
| 6 | Redis 분산 | ✅ | 높음 | 안 함 | 설정 | ✅ | 어려움 | **추가+인프라** | ✅ | **과함** |

### 각 대안의 핵심 차이

**1·2번 (락)** — 정확성은 확보됩니다. 하지만 `sleep` 하는 동안 락을 쥐고 있으면
다른 스레드는 **차례를 예약조차 못 하고** 모니터에서 대기합니다.
`synchronized`는 그 대기가 **인터럽트 불가**라 요청 취소도 안 됩니다.

**3번 (CAS)** — 이미 쓰고 있는 `AtomicLong`을 **올바르게** 쓰는 것입니다.
자기 차례를 원자적으로 예약한 뒤 **락 없이** 잡니다.
각 스레드가 자기 대기 시간을 미리 알게 되므로 timeout·interrupt를 붙이기 쉽습니다.

**4·5번 (라이브러리)** — 검증된 구현이고 지표 연동도 있습니다.
다만 호출 지점이 **한 곳**인데 의존성과 설정 표면이 늘어납니다.
Bucket4j의 burst 허용은 네이버 쿼터 정책을 모르는 상태에서 **오히려 위험**할 수 있습니다.

**6번 (Redis)** — 다중 인스턴스에서만 의미가 있습니다. 지금은 인스턴스가 1개입니다.

---

## 사람이 선택한 해결책과 이유

> **선택: 3번 CAS 슬롯 예약.** 대기 정책은 "최대 대기시간 + interrupt만".

**이 선택은 AI가 확정하지 않았습니다.** AI는 위 비교표와 추천 근거까지 제시했고,
개발자가 다음 기준으로 최종 결정했습니다.

| 판단 기준 | 결정 근거 |
|---|---|
| 문제를 제대로 푸는가 | 3번은 read-compute-write를 한 덩어리로 만든다. 원인을 정확히 제거 |
| 가장 작은 복잡도인가 | diff가 몇 줄. 새 의존성 0 |
| 왜 1·2번이 아닌가 | sleep 중 락 점유가 불필요하다. 얻는 것 없이 스레드를 묶는다 |
| 왜 4·5번이 아닌가 | 호출 지점 한 곳에 라이브러리와 설정 표면을 늘릴 이유가 없다 |
| 왜 6번이 아닌가 | 인스턴스가 1개다. **키워드 때문에 넣지 않는다** |

대기 정책을 "상한 + interrupt"까지만 넣은 이유:
리미터를 정상화하면 **모두가 앞에서 기다리는** 새 문제가 생깁니다.
동시 16이면 마지막 요청은 이론상 32초를 기다립니다. 그때 클라이언트는 이미 떠났습니다.
다만 큐·백프레셔까지는 현재 트래픽에 과합니다.

## 구현

**최종 구현입니다.** 여기 오기까지 한 번 고쳤고, 그 과정은 바로 아래에 있습니다.

```java
private void enforceMinInterval() {
    final long now = System.nanoTime();
    final long intervalNanos = minIntervalMs * 1_000_000L;
    final long maxWaitNanos  = maxWaitMs * 1_000_000L;

    long waitNanos;
    while (true) {
        long prev = nextSlotAtNanos.get();
        // Math.max로 과거를 끌어올린다. 없으면 한동안 호출이 없었을 때 버스트가 난다.
        long mySlot = Math.max(now, prev);
        waitNanos = mySlot - now;

        if (waitNanos > maxWaitNanos) {
            rateLimitRejections.increment();
            // ★ 예약하지 않고 거절한다. 이 요청은 차례를 소비하지 않는다.
            throw new ApiException(ErrorCode.RATE_LIMITED, "...");
        }
        if (nextSlotAtNanos.compareAndSet(prev, mySlot + intervalNanos)) {
            break;                 // 내 차례를 확보했다
        }
        Thread.onSpinWait();       // 다른 스레드가 먼저 예약했다. 다시 읽고 재시도.
    }

    long waitMs = waitNanos / 1_000_000L;
    if (waitMs <= 0) return;       // 내 차례가 이미 지났다

    rateLimitWaitTimer.record(waitMs, MILLISECONDS);
    try {
        Thread.sleep(waitMs);      // 락을 쥐지 않은 채로 잔다
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();   // 플래그를 되살린다
        throw new ApiException(ErrorCode.RATE_LIMITED, "...");
    }
}
```

### 왜 이게 되는가

CAS가 **성공해야만** 차례를 차지합니다. 두 스레드가 같은 `prev`를 읽어도
하나만 성공하고, 진 쪽은 새 값을 읽고 다시 줄을 섭니다.

| 스레드 | 읽은 `prev` | 확보한 차례 | 다음 예약값 |
|---|---|---|---|
| A | now | **now** (바로) | now+200 |
| B | now+200 | **now+200** | now+400 |
| C | now+400 | **now+400** | now+600 |

`sleep`은 **CAS 밖에서** 합니다. 자는 동안 아무 락도 쥐지 않으므로
뒤따라오는 스레드가 그 사이에 자기 차례를 예약할 수 있습니다.
락 방식(1·2번)과 갈리는 지점이 여기입니다.

### 거절된 요청은 차례를 소비하지 않습니다 (리뷰 지적으로 수정)

**처음 구현은 이게 아니었습니다.** `updateAndGet` 한 줄로 예약했습니다.

```java
// 수정 전 — 무조건 예약한 뒤 상한을 넘으면 거절
long mySlotNanos =
    nextSlotAtNanos.updateAndGet(prev -> Math.max(now, prev) + intervalNanos) - intervalNanos;

long waitMs = (mySlotNanos - now) / 1_000_000L;
if (waitMs > maxWaitMs) {
    rateLimitRejections.increment();
    throw new ApiException(ErrorCode.RATE_LIMITED, "...");   // ← 이미 예약한 뒤다
}
```

`updateAndGet`도 내부적으로는 CAS 루프라 **동시성은 안전합니다.**
문제는 다른 데 있었습니다 — **"무조건 갱신"이라 조건을 끼워 넣을 수 없습니다.**
그래서 거절할 요청까지 슬롯을 예약해 버렸습니다.
외부 API를 부르지도 않으면서 차례만 미래로 밀어 놓는 **유령 슬롯**입니다.

그때 코드 주석에 "빈 슬롯 하나가 생길 뿐이라 안전한 방향"이라고 적어 뒀는데
**틀렸습니다.** PR 리뷰에서 지적받아 재현했습니다.

```
상한 1s · 간격 200ms · 요청 20건 동시

실제 외부 호출 : 6회   → 예약은 1,200ms까지만 밀려야 정상
실제 예약 밀림 : 3,981ms
유령 슬롯      : 2,781ms  (= 거절 14건 × 200ms)

부하가 멈춘 뒤 정상 요청 → ❌ 거절됨
```

**아무도 네이버를 부르지 않는데 사용자만 429를 받는 상태**가 됩니다.
거절이 쌓일수록 차례가 계속 미래로 밀려 정상 요청까지 연쇄로 막힙니다.

`compareAndSet` 루프를 직접 쓰면 **거절 조건을 예약 전에 판정**할 수 있습니다.
상한을 넘으면 CAS를 아예 실행하지 않고 빠져나갑니다.
회귀 테스트 3개로 고정했고, **수정 전 코드에서는 셋 다 실패**합니다.

### `currentTimeMillis`가 아니라 `nanoTime`

벽시계는 NTP 보정으로 **뒤로 점프할 수 있습니다.**
그러면 이미 예약된 차례가 갑자기 먼 미래가 되어 모든 요청이 길게 멈춥니다.
`nanoTime`은 단조 증가라 그런 일이 없습니다.
여기서 필요한 것은 "지금 몇 시인가"가 아니라 **"얼마나 지났는가"** 입니다.

### 좋아진 것
- **외부 호출 상한이 동시성과 무관하게 지켜집니다.** 74.0 → 5.0
- 쿼터 초과로 429나 차단을 당할 위험이 줄었습니다
- 재시도 경로도 이제 차례를 지킵니다

### 대가로 잃은 것
- **동시 요청의 대기시간이 늘었습니다.** 동시 16에서 2.1초 → 31.8초
- 처리량이 제한됩니다

**이건 성능 저하가 아닙니다.** 레이트 리미터의 목적 자체가 처리량 제한입니다.
Before의 2.1초는 "빨랐던 것"이 아니라 **제한이 동작하지 않아 빨랐던 것**입니다.
32초가 불편하다면 답은 리미터를 푸는 게 아니라 **뷰포트당 호출 수를 더 줄이는 것**입니다
(이미 41 → 10으로 줄였습니다 — [CS 05](05-map-api-cache.md)).

## 이 구현이 보장하는 범위 (리뷰 지적으로 명확화)

"초당 5회 제한"은 두 가지로 읽힙니다.

```
A. 장기간 평균 호출률 ≈ 5 req/s
B. 어떤 연속된 1초 구간에서도 호출 ≤ 5
```

**이 구현은 A만 보장합니다.**

슬롯 예약은 "언제부터 호출할 수 있는가"만 정합니다.
스레드가 GC 멈춤이나 스케줄링 지연으로 슬롯보다 **늦게** 깨어나면
밀렸던 호출들이 뭉쳐서 나갑니다.

실측 — **슬롯을 앞서 받은 호출 5개**에 600ms 지연을 주입(스레드 10개, 4회 실행):

| 항목 | 값 |
|---|---|
| 슬롯 10개를 내주는 데 걸린 시간 | **1,801ms** (= (10−1) × 200ms. 리미터는 제 일을 했습니다) |
| **1초 창 최댓값** | **8~9회** ❌ (목표 5회) |
| 최소 간격 | **0ms** |

> **지연 대상을 스레드 인덱스가 아니라 "슬롯을 받은 순서"로 고르는 것이 중요합니다.**
> 어느 스레드가 어느 슬롯을 받을지는 CAS 경쟁 결과라 매번 다릅니다.
> 뒤쪽 슬롯이 밀리면 그냥 더 늦게 나갈 뿐이고, 뭉침은
> **앞 슬롯이 밀려 뒤 슬롯을 따라잡을 때** 생깁니다.
> 지연 지점도 **슬롯을 받은 뒤**여야 합니다 — 호출 전에 자면 리미터에 늦게 도착할 뿐입니다.
>
> 그리고 이 조건에서는 **관측 평균(rps)을 판정에 쓸 수 없습니다.**
> 그 값은 첫 호출~마지막 호출 구간으로 나누는데, 앞쪽을 늦추면 구간이 짧아져
> **지연을 줄수록 평균이 올라갑니다.** 측정 도구가 조건에 오염된 경우입니다.
> 그래서 지연과 무관하게 참인 것 — 슬롯 n개를 내주려면 최소 (n−1)×간격이 걸린다 —
> 으로 단정을 바꿨습니다. 리미터를 no-op으로 만들면 이 단정이 실제로 실패합니다
> (12개 중 10개 실패 확인).

### 그래서 무엇을 했나

**B를 보장하도록 고치지 않았습니다.** 호출 시각을 창 단위로 세는 구조가 필요한데,
**네이버가 strict sliding window를 요구한다는 근거가 없습니다.**
`min-interval-ms=200`이라는 값 자체도 공식 쿼터가 아니라 기존 코드에 있던 값입니다.
근거 없는 요구에 복잡도를 쓰지 않습니다.

대신 두 가지를 했습니다.

1. **테스트가 보장하지 않는 것을 단정하지 않도록 고쳤습니다.**
   처음에는 "1초 창 ≤ 6"으로 단정했는데, 이건 구현이 보장하지 않는 성질이라
   느린 머신에서 흔들릴 수 있었습니다(flaky). **장기 평균** 기준으로 바꿨습니다.
   동시성 버그가 있으면 평균이 목표의 3~15배가 되므로 판별력은 그대로입니다.
2. **성질을 기록하는 테스트를 뒀습니다** (`guaranteeIsLongRunAverageNotSlidingWindow`).
   나중에 누가 "이건 sliding window를 보장한다"고 오해하지 않도록 못 박았습니다.

### strict sliding window가 필요해지는 조건

- 네이버가 **문서로** 1초 창 기준 쿼터를 명시한 경우
- 실제로 429를 받기 시작한 경우 (지금은 `naver_api_calls_total`로 관찰만 하고 있음)

그때는 창 카운터를 붙이면 됩니다. 슬롯 예약 구조는 그대로 두고 앞단에 얹을 수 있습니다.

## 리미터의 범위

### Local Search와 Reverse Geocoding이 리미터 하나를 공유합니다

둘은 **다른 키**(`NAVER_LOCAL_*` vs `NAVER_MAP_*`)와 **다른 호스트**
(`naverapihub.apigw.ntruss.com` vs `maps.apigw.ntruss.com`)를 씁니다.
별도 상품이므로 쿼터도 별도일 가능성이 큽니다.

**그래도 분리하지 않았습니다.** 별도 쿼터라는 **문서화된 근거가 없기 때문**입니다.
공유 리미터는 "실제 허용치보다 적게 부르는" 쪽으로 틀리므로 안전한 방향입니다.
분리했다가 실제로 공유 쿼터였다면 초과하게 됩니다.

쿼터 근거를 확보하면 리미터를 API별로 나눠야 합니다. 지금은 한계로 남깁니다.

### 캐시가 리미터보다 앞에 있습니다

```
요청 → 캐시 조회 ─ HIT ─→ 반환 (외부 호출 없음, 리미터 안 거침)
              └ MISS ─→ 리미터 → 네이버 API → 캐시 저장
```

코드로 확인했습니다 — `searchLocal()`에서 캐시 조회가 `enforceMinInterval()`보다 앞에 있습니다.
**이미 올바른 순서**라 바꾸지 않았습니다.
리미터는 **외부로 나가는 호출만** 제한해야 합니다.
캐시 hit까지 기다리게 하면 아무것도 얻지 못하고 응답만 느려집니다.

테스트로 고정했습니다 — 같은 검색어 20회 요청이 **1초 미만**에 끝납니다.
리미터 뒤에 있었다면 20 × 200ms = 약 4초가 걸립니다.

### 판별력을 두 번 고쳤습니다

**첫 번째** — 처음에는 스레드당 1회만 호출했습니다.
그랬더니 **동시성 4에서 수정 전 코드가 통과**했습니다.
4건은 1초 예산(5건) 안이라 버그가 있어도 안 걸립니다.
스레드당 3회로 늘려 12건이 되게 했습니다.

**두 번째** — 처음에는 "최소 호출 간격 ≥ 200ms"로 단정했습니다.
그런데 GC 등으로 JVM이 잠깐 멈췄다 재개되면 그 직후 한 건이 곧바로 나가
간격이 짧아집니다. **멈춰 있는 동안 아무 호출도 안 나갔으므로 쿼터를 넘긴 게 아닙니다.**

그래서 **슬라이딩 1초 창**으로 바꿨습니다.

> "초당 5회"는 "연속한 두 호출이 200ms 떨어져 있어야 한다"가 아니라
> **"어떤 1초를 잘라도 5회를 넘지 않아야 한다"** 는 뜻이라고 생각했습니다.

**이것도 틀렸습니다.** PR 리뷰에서 잡혔습니다 —
*구현은 장기 평균만 보장하는데 테스트는 슬라이딩 윈도우를 단정하고 있다.*

맞는 지적이었습니다. 슬라이딩 창은 **쿼터가 요구하는 성질**일 수는 있어도
**이 구현이 보장하는 성질**은 아닙니다. 보장하지 않는 것을 단정하면
느린 머신에서 흔들립니다(flaky).

> **최종 상태** — 판별 기준은 **장기 평균**(`RATE_TOLERANCE = 1.5`)이고,
> 슬라이딩 창은 단정이 아니라 **기록**으로만 남깁니다.
> 위 [이 구현이 보장하는 범위](#이-구현이-보장하는-범위-리뷰-지적으로-명확화) 참고.

기준을 두 번 고쳐서야 구현이 실제로 보장하는 것에 닿았습니다.

## 다중 인스턴스 한계 — 재현했습니다

"인스턴스가 2개면 2배가 된다"는 추론으로 두지 않고 실제로 띄워 봤습니다.

### 방법

같은 jar 로 JVM 두 개를 띄우고(`:8081`, `:8082`) 같은 스텁을 보게 했습니다.
캐시는 껐습니다 — 켜져 있으면 hit 이 되어 외부로 나가지 않아 호출률을 잴 수 없습니다.
각 인스턴스의 `naver_api_calls_total` 지표와 스텁이 받은 총 호출 수를 함께 셌습니다.

> 컨테이너가 아니라 JVM 을 직접 띄웠습니다. 여기서 문제가 되는 것은
> 컨테이너 격리가 아니라 **`nextSlotAtNanos` 가 JVM 안의 필드**라는 사실입니다.

### 결과

| 조건 | 인스턴스별 | **네이버가 받는 합산** | 목표 |
|---|---:|---:|---:|
| JVM 프로세스 1개 (동시 4건 × 3회) | 5.2 req/s | **5.2 req/s** | 5.0 ✅ |
| **JVM 프로세스 2개** (각 동시 4건 × 3회) | 각 **5.0** | **10.0 req/s** | 5.0 ❌ |

스텁이 받은 실제 호출: 1개일 때 120회, 2개일 때 **240회**.

**각 인스턴스는 자기 몫을 정확히 지킵니다.** 5.0 req/s 로 흠잡을 데가 없습니다.
그런데 **네이버가 보는 것은 합산**입니다. 리미터가 지키는 단위와
쿼터가 적용되는 단위가 다릅니다.

```
인스턴스 A → nextSlotAtNanos(A) → 5.0 req/s
인스턴스 B → nextSlotAtNanos(B) → 5.0 req/s
                                   ↓
                      네이버가 보는 것 → 10.0 req/s
```

인스턴스를 n 개로 늘리면 `5 × n` 이 됩니다. 이건 버그가 아니라
**JVM 안의 상태로 프로세스 밖의 자원을 제한하려 할 때 생기는 구조적 한계**입니다.

### 다중 인스턴스에서 깨지는 것은 리미터만이 아닙니다

AWS 배포를 준비하며 저장소를 훑다가 더 심각한 것을 찾았습니다([CS 12](12-cloud-operation.md)).

| 위치 | 문제 |
|---|---|
| `NaverApiClient` `nextSlotAtNanos` 필드 | 리미터 — 쿼터를 넘길 수 있음 |
| `NaverResponseCache` | 캐시 — 인스턴스마다 따로 채움 (비효율일 뿐) |
| **`PasswordResetService:56`** `resetTokens` | **비밀번호 재설정 토큰이 메모리에.** A 에서 발급 → B 로 라우팅되면 "토큰 없음" |
| **`EmailVerificationService:27`** `verificationCodes` | **이메일 인증코드가 메모리에.** 같은 문제 |

**뒤의 둘이 더 급합니다.** 리미터는 쿼터를 조금 넘기는 문제지만,
이 둘은 **사용자가 비밀번호를 못 바꾸고 가입을 못 끝내는** 문제입니다.
다중 인스턴스로 가려면 리미터보다 이것부터 옮겨야 합니다.

## 남은 한계

- **JVM 안에서만 유효합니다.** 위 실험에서 확인했습니다 — JVM 프로세스 2개 → 10.0 req/s

- **`min-interval-ms=200`의 근거가 약합니다.** 네이버가 공표한 쿼터가 아니라
  기존 코드에 있던 값을 설정으로 옮긴 것입니다. 실제 허용치 확인이 필요합니다.
- **Local Search와 Reverse Geocoding이 리미터를 공유합니다.** 위 참고.
- **큐·백프레셔가 없습니다.** 상한을 넘으면 즉시 거절할 뿐, 대기열 크기를 관리하지 않습니다.
- **거절이 실제 트래픽에서 얼마나 나는지 모릅니다.** 배포는 했지만 실사용 트래픽이 없습니다.
- **거절에 대한 알림 규칙이 없습니다.**

**두 번째 지적은 제 테스트가 틀렸다는 뜻이기도 했습니다.**
"1초 창 ≤ 6"을 단정하고 있었는데 구현이 그걸 보장하지 않습니다.
느린 머신에서 흔들렸을 것입니다. 리뷰가 없었으면 CI가 가끔 빨개지는 이유를 몰랐을 것입니다.

**셀프 리뷰만으로는 부족합니다.** 셀프 리뷰에서 재시도 경로 결함을 찾긴 했지만,
자기가 "안전하다"고 판단하고 주석까지 써 둔 것은 스스로 의심하지 않습니다.
유령 슬롯이 정확히 그런 경우였습니다 —
코드에 "빈 슬롯 하나가 생길 뿐이라 안전한 방향"이라고 적어 두었습니다.

## AI 보조 워크플로우

이 작업은 [AI 보조 개발 워크플로우](../ai-development-workflow.md)를 처음 적용한 사례입니다.

### AI가 한 것

| 단계 | 내용 |
|---|---|
| 코드 탐색 | `NaverApiClient.enforceMinInterval()`의 read→sleep→write 구조 확인, 캐시-리미터 순서 확인 |
| 실패 재현 | 결정적 동시성 테스트 작성, 동시성별 측정 하네스 구현 |
| 대안 비교 | 6개 후보를 10개 기준으로 비교 |
| 구현 | CAS 슬롯 예약 + nanoTime + 대기 정책 |
| 테스트 확장 | 대기 정책·interrupt·캐시 상호작용 |
| 측정 자동화 | `./gradlew rateLimitMeasurement` |
| 셀프 리뷰 | **재시도 루프가 리미터를 건너뛰는 것**을 발견해 수정 |

### 사람이 한 것

| 결정 | 내용 |
|---|---|
| **구현 방식 선택** | 6개 대안 중 CAS 슬롯 예약 채택 |
| **대기 정책 범위** | "상한 + interrupt"까지만. 큐·백프레셔는 현재 규모에 과하다고 판단 |
| **Redis 배제** | 인스턴스 1개. 키워드용 도입 거부 |
| **리미터 범위** | 근거 없이 API별로 분리하지 않기로 결정 |
| **측정 타당성** | 기존 40.2를 재사용하지 않기로 판단 |

### 이 절차가 실제로 막아 준 것

1. **기존 문서의 40.2를 그대로 옮겨 적지 않았습니다.** 재현을 시도했고, 안 되는 이유를 찾았습니다.
2. **판별력 없는 테스트를 걸러냈습니다.** 동시성 4에서 버그가 있어도 통과하던 것을 잡았습니다.
3. **흔들리는 단정을 고쳤습니다.** 최소 간격 → 슬라이딩 1초 창.
4. **셀프 리뷰에서 두 번째 결함을 찾았습니다.** 재시도 경로.

> AI를 **분석·재현·구현·측정 보조**로 쓰고,
> **설계 판단과 검증은 개발자가** 했습니다.
