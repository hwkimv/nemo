# Case Study — 앨범 목록 N+1 제거와 측정

> **한 줄 요약** — 앨범 100개 조회에 DB 쿼리가 202번 나갔습니다. 4번으로 줄여 응답시간을 99ms → 11ms로 낮췄고, **환경 차이를 걷어내기 위해 같은 시각·같은 DB에서 이전 코드를 다시 측정**해 개선분을 분리했습니다.

| | |
|---|---|
| **기간** | 2026-08-14 |
| **범위** | Backend — album · timeline · photo 조회 경로 |
| **결과** | 앨범 목록 SQL 202 → 4, 응답 avg 98.91ms → 10.91ms (-89%) |
| **증거** | [측정 원자료](../evidence/2026-08-14-after-and-index.md) · [Before 기준선](../evidence/2026-08-05-baseline.md) |

---

## Problem

2026-08-05에 조회 성능 기준선을 측정해 두었습니다.

| 흐름 | SQL 수 | k6 avg | k6 p95 |
|---|---:|---:|---:|
| **앨범 목록** | **202** | **121.21ms** | **144.70ms** |
| 사진 목록 | 2 | 15.13ms | 20.58ms |
| 타임라인 | 1 | 18.31ms | 21.38ms |

사용자 1명이 앨범 100개를 보는데 **쿼리가 202번** 나갔습니다. 앨범이 1,000개면 2,002번이 됩니다.

내역을 뜯어보면 정확히 이렇습니다.

```
  1  앨범 목록 조회
100  앨범마다 LAZY photos 컬렉션 접근   ← 사진 "개수"를 세려고 사진을 다 불러옴
100  앨범마다 공유 여부 exists 조회
  1  공유받은 앨범 목록
────
202
```

원인 코드는 한눈에 보입니다.

```java
albumRepository.findByUserId(userId).stream().map(album -> {
    autoSetThumbnailIfMissing(album);              // album.getPhotos() 접근 = 쿼리 1번
    int photoCount = album.getPhotos().stream()... // 개수 세기
    boolean sharedFlag = albumShareRepository
            .existsByAlbumIdAndStatusAndActiveTrue(...);  // 쿼리 1번 더
})
```

`album.getPhotos()`는 LAZY라 **건드리는 순간** 쿼리가 나갑니다. `.map()` 안에서 앨범마다 건드리니 앨범 수만큼 쿼리가 나간 것입니다.

---

## Analyze / Constraints

**목록 화면이 실제로 필요한 값은 두 개뿐입니다** — 사진 장수, 커버 이미지 URL.
사진 엔티티를 통째로 메모리에 올릴 이유가 없습니다.

**제약** — 응답 계약을 바꾸지 않기로 했습니다. Flutter 클라이언트가 이미 이 응답을 쓰고 있어서, 성능을 고치다 기능이 바뀌면 안 됩니다.

같이 발견한 것: **기존 `autoSetThumbnailIfMissing()`은 목록을 "조회"하면서 앨범 엔티티를 수정**하고 있었습니다. 읽기 작업이 데이터를 바꾸는 것은 예상 밖의 동작입니다.

## Options

| 방법 | 장점 | 단점 | 선택 |
|---|---|---|---|
| **EAGER 전환** | 한 줄이면 끝 | 사진이 **필요 없는** 모든 Album 조회에까지 로딩 비용이 퍼짐 | ❌ |
| **Fetch Join** | 한 번에 가져옴 | 1:N 조인이라 앨범 행이 사진 수만큼 중복. 페이징과 함께 쓰면 메모리 페이징으로 전락 | ❌ |
| **목록 전용 projection + 일괄 조회** | 필요한 컬럼만, 쿼리 수 고정 | 코드가 조금 늘어남 | ✅ |

세 번째를 골랐습니다. 목록에 필요한 것이 명확하므로, 그것만 가져오는 쿼리가 가장 명시적입니다.

---

## Action

### 1. 앨범 목록 N+1 제거 — 쿼리 수를 앨범 개수와 무관하게 고정

```
① 소유 앨범 목록
② 공유받은 앨범 목록          JOIN FETCH로 Album까지 한 번에
③ 해당 앨범들의 사진 정보     ← 100번이 1번으로
④ 공유 중인 앨범 id 목록      ← 100번이 1번으로
```

③은 컬럼 4개만 뽑는 전용 projection입니다.

```java
SELECT new AlbumPhotoRow(a.id, p.thumbnailUrl, p.imageUrl, p.createdAt)
FROM Album a JOIN a.photos p
WHERE a.id IN :albumIds AND p.deleted = false
```

목록용 커버 계산은 엔티티를 건드리지 않는 `resolveCoverUrl()`로 분리했습니다. **표시 규칙은 완전히 동일합니다.**

### 2. 타임라인 — 기간 필터를 JVM에서 DB로

한 달치를 보려고 몇 년치를 다 읽고 Java에서 버리고 있었습니다. 여기서 조용히 틀리기 쉬운 세 곳을 짚었습니다.

| 함정 | 처리 |
|---|---|
| 촬영일이 없는 사진 | `COALESCE(taken_at, created_at)` — 기존 "촬영일 없으면 업로드일" 규칙을 그대로 DB로 옮김. `taken_at`만 봤다면 그 사진들이 **조용히 사라졌을** 자리 |
| 월말 시간 | 반열림 구간 `[start, end)`. `<= 월말`로 했다면 **말일 23:59:59 사진이 빠짐** |
| 12월 다음 달 | `plusMonths(1)`. `month + 1`이었다면 12월에서 **13월**이 되어 터짐 |

연도 없이 월만 지정하는 경우(모든 해의 N월)는 하나의 연속 구간으로 표현할 수 없어 기존 방식을 그대로 뒀습니다.

### 3. 앨범 목록 페이지네이션 — 메모리에서 DB로

N+1을 없앤 뒤에도 Controller는 전체 목록을 만든 뒤 메모리에서 정렬하고 `subList()`로 잘랐습니다.

```
1단계: DB에서 정렬·페이징까지 끝내고 → 이 페이지의 앨범 id만 받는다
2단계: 그 id들에 대해서만 → 장수·커버·공유여부를 채운다
```

소유 앨범과 공유받은 앨범은 다른 테이블이라 `UNION ALL`로 합칩니다. 정렬 기준이 요청마다 달라져 native SQL을 썼고, **정렬 컬럼 문자열은 enum에서만** 나오므로 사용자 입력이 SQL에 직접 들어가지 않습니다.

**정렬 값이 같을 때를 대비해 `album_id`를 보조 정렬 기준으로 넣었습니다.** 이게 없으면 같은 시각에 만든 앨범이 페이지 경계에서 중복되거나 누락됩니다. 기존 메모리 정렬에는 이 보장이 없었습니다.

## Result

### ⚠️ 측정하다 발견한 함정 — 이 사례의 핵심

처음엔 8월 5일 기준선과 오늘 값을 그냥 비교하려 했습니다.

| API | 8월 5일 | 오늘 | 배율 |
|---|---:|---:|---:|
| 앨범 | 121.21ms | 10.91ms | 11.1배 |
| 사진 | 15.13ms | 4.22ms | **3.6배** |

**사진 목록은 코드를 한 줄도 바꾸지 않았는데 3.6배 빨라져 있었습니다.**
9일 사이에 머신 상태 자체가 빨라진 것입니다. 이대로 "11배 개선"이라고 쓰면 **환경 덕분에 빨라진 몫까지 내 성과로 가져가는** 셈입니다.

그래서 **같은 세션·같은 DB·같은 시드에서 이전 코드를 다시 측정**했습니다.

- 성능 개선 커밋 2개만 revert한 worktree를 만들고, 나머지 코드는 동일하게 유지
- **사진 목록을 대조군**으로 삼음 — 코드를 안 바꿨으니 이 값이 안 변해야 측정을 믿을 수 있음

### 같은 환경 Before / After

| 항목 | Before | After | 변화 |
|---|---:|---:|---|
| 앨범 목록 SQL | **202 / 202 / 202** | **4 / 4 / 4** | -98% |
| 앨범 목록 avg | **98.91ms** | **10.91ms** | **-89%** |
| 앨범 목록 p95 | 114.20ms | 15.19ms | -87% |
| 타임라인 avg | 8.27ms | 4.40ms | -47% |
| **사진 목록 (대조군)** | 4.72ms | 4.22ms | **변화 없음** ✅ |

**대조군이 평평하다는 것이 이 수치의 신뢰 근거입니다.**
8월 5일에 기록된 202 쿼리도 정확히 재현되어, 기준선 자체가 신뢰할 만하다는 것도 함께 확인했습니다.

### 페이지네이션 — 배율이 아니라 기울기

| 앨범 수 | 메모리 페이징 | DB 페이징 |
|---:|---:|---:|
| 100개 | 18.57ms | **8.10ms** |
| 5,000개 | **74.26ms** | **8.10ms** |
| 5,000개 중 마지막 페이지 | — | 8.47ms |

앨범이 **50배**가 되는 동안 이전 방식은 4배 느려졌고, 새 방식은 **변하지 않았습니다.**

> **솔직하게** — 앨범 100개 규모에서는 k6 기준 9.83ms로 N+1만 고친 상태(10.91ms)와 사실상 같습니다. **지금 데이터에서는 병목이 아니었습니다.** 이 변경의 값어치는 현재 수치가 아니라 데이터가 늘어날 때 드러납니다.

### 인덱스 판단

> 원칙: 인덱스를 먼저 만들지 않는다. 실행 계획에서 병목을 확인한 뒤 결정한다.

1,000행에서는 모든 쿼리가 1ms 미만이라 판단 근거가 없었습니다. **사진 20만 장을 넣고** 다시 비교했습니다.

| 쿼리 | 인덱스 없음 | 인덱스 있음 | 배율 |
|---|---:|---:|---:|
| 사진 목록 첫 페이지 | 14.469ms | **0.077ms** | **188배** |
| 타임라인 한 달 | 15.534ms | 4.535ms | 3.4배 |

사진 목록이 188배인 이유: `ORDER BY taken_at DESC LIMIT 20`에서 인덱스가 이미 정렬된 순서를 주므로 **20건 읽고 즉시 멈춥니다.** 정렬 단계가 통째로 사라집니다.

**그런데 적용하지 못했습니다.** 부분 인덱스(`WHERE deleted = false`)·정렬 방향(`DESC`)·표현식(`COALESCE`)은 JPA `@Table(indexes = ...)`로 **표현할 수 없고**, 저장소에 마이그레이션 도구가 없습니다. SQL은 `tools/performance/sql/indexes.sql`에 두고 비용(20만 장 기준 각 6.2MB, 테이블의 약 20%)도 함께 기록했습니다.

## Limit / Next Condition

- **낮은 동시성 로컬 측정입니다.** 1 VU 기준이며 최대 처리량이나 운영 지연시간을 뜻하지 않습니다.
- **인덱스는 마이그레이션 도구 도입 후 적용**합니다. 지금 넣으면 운영 반영 절차가 없습니다.
- **`getAlbums()` 전체 목록 메서드가 남아 있습니다.** 목록 화면은 더 이상 쓰지 않지만 다른 호출부가 있어 제거하지 않았습니다.
- 측정 중 **S3가 꺼져 있으면 앱이 아예 기동하지 않는 것**을 발견했습니다. 읽기 전용 API만 쓸 때도 그렇습니다. 별도 과제입니다.
