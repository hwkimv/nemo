# AI 보조 개발 워크플로우

> 이 문서는 **이번 저장소에서 실제로 돌려 본 절차**만 적습니다.
> 팀 도입 사례나 조직 차원의 프로세스가 아니라, **개인 프로젝트에서 반복 가능하게
> 정리한 작업 방식**입니다.

## 왜 만들었나

AI에게 "이거 고쳐줘"라고 하면 코드는 나옵니다. 문제는 그 다음입니다.

- 정말 그 문제가 있었는지 **증명되지 않습니다**
- 왜 그 해결책인지 **다른 선택지와 비교되지 않습니다**
- 좋아졌다는 숫자가 **어떻게 나온 건지 알 수 없습니다**
- 결과적으로 **면접에서 설명할 수 없는 코드**가 남습니다

그래서 순서를 고정했습니다. **각 단계의 산출물이 다음 단계의 입력**이 되고,
설계 판단은 사람이 합니다.

---

## 흐름

```
Issue / Problem
      ↓
AI Repository Analysis        ← 근거(파일:라인) 없이는 다음으로 못 감
      ↓
AI Failure Reproduction       ← 실패하는 테스트가 없으면 문제가 아님
      ↓
AI Solution Candidates        ← 최소 3개, 같은 기준으로 비교
      ↓
Human Design Decision         ← ★ 사람이 고른다
      ↓
AI Implementation
      ↓
Automated Tests               ← 재현 테스트가 통과로 바뀌어야 함
      ↓
Independent AI Review         ← 구현한 세션과 분리
      ↓
Human Verification
      ↓
PR
```

## 단계별

| 단계 | AI 역할 | 사람 역할 | 산출물 | 완료 조건 |
|---|---|---|---|---|
| **1. 코드 분석** | 실제 파일을 읽고 흐름·경계를 정리 | 범위 지정 | 파일 경로 + 라인 번호 + 코드 인용 | 추측 문장이 하나도 없음 |
| **2. 실패 재현** | 깨지는 테스트 작성 | 재현 조건이 현실적인지 확인 | 실패하는 테스트 + 실측 수치 | **수정 전 코드에서 실제로 실패** |
| **3. 대안 제시** | 후보 나열, 같은 기준으로 비교 | — | 비교표 + 추천 + 근거 | 최소 3개, 기준이 동일 |
| **4. 설계 결정** | 추천만 | **★ 최종 선택** | 선택 + 이유 | 왜 다른 걸 안 골랐는지 설명 가능 |
| **5. 구현** | 코드 작성 | 방향 이탈 감시 | diff | 기존 테스트 전부 통과 |
| **6. 테스트/측정** | 테스트 확장, 측정 자동화 | 측정 방법 타당성 판단 | Before/After 표 | **같은 도구로 양쪽 측정** |
| **7. 셀프 리뷰** | 자기 구현의 약점 탐색 | — | 발견 목록 | 최소 1건은 찾을 것 |
| **8. 독립 리뷰** | **다른 세션**이 공격적으로 검토 | 지적 채택 여부 결정 | 리뷰 결과 | 구현 세션과 분리됨 |
| **9. 문서화** | Case Study·PR 초안 | 과장 여부 검수 | 문서 | 측정 안 한 건 "안 했다"고 적힘 |

## 실제 적용 예 — 레이트 리미터 (2026-08-21)

이 워크플로우로 처리한 첫 사례입니다.
([CS 11](case-studies/11-rate-limiter-concurrency.md))

| 단계 | 실제로 일어난 일 |
|---|---|
| 1. 분석 | `NaverApiClient.java:403` `enforceMinInterval()`의 read→sleep→write 구조 확인. 캐시가 리미터보다 **앞**이라는 것도 코드로 확인 |
| 2. 재현 | 동시 4/8/16에서 **74.0 req/s**(목표 5.0) 측정. `min_gap_ms=0` |
| 3. 대안 | `synchronized` / `ReentrantLock` / CAS / Resilience4j / Bucket4j / Redis 6개를 10개 기준으로 비교 |
| 4. **결정** | **사람이 CAS 슬롯 예약 선택.** 대기 정책은 "상한 + interrupt만" 선택 |
| 5. 구현 | `updateAndGet` 슬롯 예약 + `nanoTime` |
| 6. 측정 | 같은 하네스로 After 측정 → 모든 동시성에서 **5.0 req/s** |
| 7. 셀프 리뷰 | **429 재시도가 리미터를 건너뛰는 것**을 스스로 발견해 수정 |
| 8. 독립 리뷰 | `prompts/engineering/review-pr.md`로 별도 세션에 전달 |
| 9. 문서화 | CS 11 + PR 본문 |

### 이 절차가 실제로 막아 준 것

- **2단계**에서 기존 문서의 `40.2 req/s`가 지금 코드로는 재현되지 않는다는 걸 발견했습니다.
  뷰포트당 호출 수가 41 → 10으로 바뀌었기 때문입니다.
  절차가 없었으면 옛 숫자를 그대로 옮겨 적었을 것입니다.
- **2단계**에서 처음 만든 동시성 테스트가 **동시성 4에서는 버그가 있어도 통과**했습니다.
  스레드당 호출을 1회 → 3회로 늘려 판별력을 확보했습니다.
- **6단계**에서 처음 쓴 "최소 호출 간격" 기준이 GC 멈춤 때문에 흔들렸습니다.
  쿼터가 실제로 요구하는 **슬라이딩 1초 창** 기준으로 바꿨습니다.
- **7단계**에서 재시도 경로의 구멍을 찾았습니다.

## 규칙

1. **근거 없는 문장 금지.** "~일 것이다"는 분석이 아니다. 파일과 라인을 댄다.
2. **재현 없는 수정 금지.** 실패하는 테스트가 없으면 문제가 있다고 말하지 않는다.
3. **설계 결정은 사람이.** AI는 선택지와 근거까지. 고르는 건 사람.
4. **같은 도구로 Before/After.** 다른 방법으로 잰 숫자는 비교가 아니다.
5. **측정 안 한 건 "안 했다"고 쓴다.** 추정치를 측정치처럼 쓰지 않는다.
6. **리뷰는 다른 세션에서.** 자기가 쓴 코드를 자기가 승인하지 않는다.
7. **키워드 때문에 기술을 넣지 않는다.** 필요 없으면 "왜 안 넣었는지"를 쓴다.

## 한계

- **1인 프로젝트 기준입니다.** 여러 사람이 붙었을 때의 조율은 다뤄지지 않았습니다.
- **독립 리뷰가 자동화돼 있지 않습니다.** 프롬프트를 사람이 다른 세션에 붙여넣습니다.
- **사례가 아직 적습니다.** 이 문서는 레이트 리미터 작업 하나로 정리한 것이고,
  다른 유형(예: UI, 데이터 마이그레이션)에서도 맞는지는 확인하지 않았습니다.
