## 1. 먼저 알아야 할 배경 개념 3가지

이 문서를 읽는 데 필요한 최소한의 개념만 정리한다.

### 1-1. Access Token은 "임시 출입증"이다

로그인하면 서버가 출입증(Access Token)을 준다. 이후 요청마다 이 출입증을 보여준다.
**출입증 번호만 알면 누구든 그 사람 행세를 할 수 있다.** 그래서 이 값이 어딘가에 기록되면 안 된다.

### 1-2. N+1 문제

앨범 목록을 보여줄 때 이런 코드가 있다고 하자.

```text
앨범 목록을 가져온다              → SQL 1번
그리고 앨범마다 사진 개수를 센다   → 앨범이 100개면 SQL 100번
```

총 101번. 앨범이 1,000개면 1,001번. **"목록 1번 + 항목 개수만큼 N번"** 이라서 N+1 문제라고 부른다.
DB 왕복 한 번이 아무리 빨라도 100번이면 느려진다.

### 1-3. 트랜잭션과 readOnly

트랜잭션은 "이 작업들은 전부 성공하거나 전부 취소된다"는 묶음이다.
`readOnly = true`는 "이 안에서는 읽기만 한다"는 선언인데, 이걸 붙여두고 몰래 쓰기를 하면
**변경이 조용히 사라질 수 있다.** 에러도 안 난다. 그래서 더 위험하다.

## 2. P0-1. 로그에 찍히던 로그인 토큰 제거

### 무엇이 문제였나

`LogConfig.java`가 모든 API 요청마다 이 줄을 실행했다.

```java
log.info("Authorization={}", req.getHeader("Authorization"));
```

즉 **모든 사용자의 Access Token 전체가 서버 로그 파일에 그대로 남고 있었다.**

### 왜 문제인가

로그는 생각보다 많은 곳에 복사된다. 개발자 PC 터미널, 로그 수집 서버, 운영 콘솔, 에러 리포트.
그 중 한 곳만 새어도 **토큰 만료 전까지 그 사용자의 계정을 그대로 쓸 수 있다.**
비유하자면 아파트 출입 카드 번호를 게시판에 매일 붙여두는 것과 같다.

### 어떻게 고쳤나

**① 토큰 로그를 삭제했다.** 대신 비밀이 아닌 정보만 남긴다.

```java
log.info("[REQ] {} {} status={} {}ms",
        req.getMethod(), req.getRequestURI(), res.getStatus(), elapsedMs);
```

앞 몇 글자만 남기는 것도 하지 않았다. 토큰은 부분만 있어도 위험하고, "일부는 괜찮다"는 기준이 생기면 관리가 안 된다.

**② 대신 요청 추적용 Request ID를 도입했다.** (`RequestIdFilter.java`)

토큰을 지웠으니 "어느 요청이 문제였는지" 찾을 다른 방법이 필요하다.
이제 요청마다 짧은 ID가 붙고, 그 요청이 남기는 **모든 로그 줄에 같은 ID가 찍힌다.**

```text
INFO [a3f9c1d2] [REQ] GET /api/albums status=200 42ms
INFO [a3f9c1d2] ... 같은 요청의 다른 로그도 같은 ID
```

이 ID는 응답 헤더 `X-Request-Id`로도 돌려준다.
그래서 **"앱에서 오류 났어요" → 그 화면의 X-Request-Id → 로그 검색 → 그 요청만 정확히 추적**이 가능하다.

> 이건 개선 문서의 "6. 구조화 로그 + Request/Trace ID" 항목의 기반이기도 하다.

### 어떻게 확인했나

`RequestLoggingSecretsTest.java` — 3개 테스트

- 가짜 토큰을 담아 요청을 보내고, **로그 문자열에 토큰 전체·앞 16글자·`Bearer`·`Authorization` 어느 것도 없음**을 검증
- 동시에 method·URI·status는 **여전히 남는지** 검증 (지나치게 지워서 추적 불가가 되면 안 되므로)
- Request ID가 MDC와 응답 헤더에서 **같은 값**인지, 요청 종료 후 정리되는지 검증
- 클라이언트가 `X-Request-Id`에 개행 문자를 넣어 **가짜 로그 줄을 주입**하려 하면 거부되는지 검증

### 남은 것

- QR payload, 소셜 로그인 provider token도 같은 기준으로 점검 필요 (이번 범위 밖)

## 3. P0-2. 남의 사진을 내 앨범에 넣을 수 있던 문제 ⚠️ 가장 위험했던 항목

### 무엇이 문제였나

앨범을 만들 때 이런 코드였다.

```java
List<Photo> photos = photoRepository.findAllById(req.getPhotoIdList());
```

`findAllById`는 **"이 ID들 가져와"** 일 뿐이다. 그 사진이 누구 것인지 묻지 않는다.
삭제 여부만 걸렀을 뿐, **소유자 확인이 아예 없었다.**

### 왜 문제인가

사진 ID는 그냥 숫자다. 사용자 A가 `photoIdList: [1, 2, 3]`을 보내면
그게 사용자 B의 사진이어도 **A의 앨범에 들어가고, 앨범 상세와 다운로드 URL로 B의 사진이 보인다.**

기존 코드에 `canManagePhotos()`라는 권한 검사가 있긴 했다. 하지만 그건
**"이 앨범을 수정할 수 있는가"** 만 확인한다.
**"이 사진을 쓸 수 있는가"** 는 완전히 다른 질문인데 아무도 묻지 않았다.

> 자기 집 냉장고 문을 열 권한이 있다고, 남의 음식을 넣을 권한이 생기는 건 아니다.

게다가 `coverPhotoId`(대표 사진)는 **별도 경로**로 처리되고 있었다.
목록 쪽만 막았다면 커버 경로로 그대로 뚫렸을 것이다.

### 어떻게 고쳤나

**① Repository 조회 자체에 소유자 조건을 넣었다.**

```java
List<Photo> findAllByIdInAndUserIdAndDeletedIsFalse(Collection<Long> ids, Long userId);
```

남의 사진 ID는 **애초에 조회 결과에 나오지 않는다.** 나중에 거르는 게 아니라 처음부터 안 가져온다.

**② 하나라도 못 쓰면 요청 전체를 실패시킨다.** (`requireUsablePhotos()`)

```java
Set<Long> uniqueIds = new LinkedHashSet<>(requestedIds);   // 중복 제거 후 개수 비교
List<Photo> usable = photoRepository.findAllByIdInAndUserIdAndDeletedIsFalse(uniqueIds, userId);

if (usable.size() != uniqueIds.size()) {
    throw new ApiException(ErrorCode.PHOTO_NOT_USABLE);
}
```

**왜 "일부만 조용히 넣기"를 안 했나:**
사용자가 10장을 골랐는데 7장만 들어가면 뭐가 왜 빠졌는지 알 수 없다.
그리고 공격자 입장에서는 **"어떤 ID가 통과하는지" 알려주는 신호**가 된다.

**③ 오류 코드를 하나로 합쳤다.** — `PHOTO_NOT_USABLE` (403)

"없는 사진 / 삭제된 사진 / 남의 사진"을 **구분해서 응답하지 않는다.**
구분해주면 `1, 2, 3, ...`을 넣어보며 **어떤 ID가 실재하는지 알아내는 탐색 통로**가 되기 때문이다.

**④ 커버 사진 경로에도 같은 검증을 적용했다.**

### 정한 정책

> **요청자가 소유한, 삭제되지 않은 사진만 앨범에 넣을 수 있다.**

공유 앨범의 EDITOR라도 남의 사진은 못 가져온다. 현재 규모에서 가장 단순하고 안전한 기본값이다.
공유 편집 정책이 실제로 필요해지면 그때 **명시적으로** 넓힌다. (넓히는 건 쉽고, 좁히는 건 어렵다)

### 어떻게 확인했나

`AlbumPhotoOwnershipTest.java` — 7개 테스트. 사용자 A·B를 실제로 만들어 재현한다.

| 테스트 | 확인 내용 |
|---|---|
| 정상 케이스 | 내 사진으로 앨범 생성은 잘 된다 |
| photoIdList에 남의 사진 | 403 실패 |
| coverPhotoId에 남의 사진 | 403 실패 (별도 경로도 막혔는지) |
| 내 사진 + 남의 사진 섞기 | **전체 실패**, 앨범도 안 만들어짐 (부분 성공 없음) |
| 삭제된 사진 / 없는 ID | 같은 오류 코드로 실패 (탐색 방지) |
| 기존 앨범에 남의 사진 추가 | 403 실패 |
| 같은 ID 두 번 보내기 | 중복 없이 1장만 추가 |

## 4. P0-3. 토큰 재발급 시 DB 변경이 사라질 수 있던 문제

### 무엇이 문제였나

`AuthService.refresh()`에 이렇게 붙어 있었다.

```java
@Transactional(readOnly = true)   // "읽기만 합니다"
public RefreshResponse refresh(RefreshRequest request) {
```

그런데 메서드 안에서는 **쓰기를 하고 있었다.**

- 만료된 Refresh Token 삭제
- 만료가 임박하면 새 토큰으로 교체(회전) 후 저장

### 왜 문제인가

`readOnly = true`면 Hibernate가 flush 모드를 MANUAL로 둔다.
쉽게 말해 **"DB에 반영해"라는 지시를 자동으로 내리지 않는다.**

무서운 점은 **에러가 안 난다**는 것이다. 코드는 정상 종료되고, 응답도 나가고, 변경만 조용히 사라진다.
사용자 입장에서는 **새 토큰을 받았는데 서버 DB에는 옛날 토큰이 남아 있어, 다음 요청에서 갑자기 로그아웃**되는 식으로 나타난다.

### 어떻게 고쳤나

**① `readOnly` 선언을 제거했다.** 클래스에 이미 `@Transactional`이 있으므로 그걸 따르게 했다.

**② 그리고 고치는 과정에서 두 번째 버그를 발견했다.**

만료 토큰 처리가 이렇게 되어 있었다.

```java
refreshTokenRepository.delete(stored);      // 지우고
throw new ApiException(INVALID_TOKEN);      // 에러 던짐
```

`readOnly`를 떼도 이건 여전히 안 된다. **예외가 트랜잭션을 롤백시키면서 삭제까지 되돌린다.**
즉 만료된 토큰이 DB에 영원히 쌓인다.

그래서 삭제만 **독립된 트랜잭션**으로 분리했다. (`RefreshTokenMaintenance.java`)

```java
@Transactional(propagation = Propagation.REQUIRES_NEW)
public void deleteInSeparateTransaction(RefreshToken token) { ... }
```

우리가 원하는 건 사실 **서로 다른 두 가지 일**이다.
"이 요청은 실패시킨다(401)" 와 "쓸모없어진 데이터는 치운다".
`REQUIRES_NEW`가 정확히 그 의도를 표현한다.

> 별도 클래스로 만든 이유: 같은 클래스 안에서 자기 메서드를 부르면 Spring 프록시를 타지 않아
> `@Transactional`이 **아무 효과가 없다.** 흔히 빠지는 함정이다.

### 어떻게 확인했나

`AuthServiceRefreshTransactionTest.java` — 3개 테스트.
핵심은 **"트랜잭션 밖에서 DB를 다시 읽어" 확인**한다는 점이다. (`em.clear()` 후 재조회)

| 상황 | 기대 |
|---|---|
| 만료된 토큰으로 재발급 시도 | 401 실패 + **해당 row가 DB에서 실제로 삭제됨** |
| 만료 임박 토큰 | 회전되고, **응답으로 준 새 토큰이 DB 저장값과 일치** |
| 아직 여유 있는 토큰 | 회전 안 함, 불필요한 쓰기 없음 |

**이 주장은 실제로 확인했다.** `@Transactional`을 다시 `@Transactional(readOnly = true)`로 되돌리고 테스트를 돌리자
"만료 임박 토큰은 회전되고, 응답의 새 토큰과 DB 저장값이 일치한다"가 **실패**했다.
즉 회전된 토큰이 DB에 커밋되지 않는다는 것이 추측이 아니라 재현된 사실이다. (확인 후 수정본으로 복원)

> ⚠️ 정직성 메모: 이 테스트는 **H2**에서 돈다. flush 유실은 Hibernate 레벨 동작이라 H2로도 재현되지만,
> 운영 PostgreSQL 동작까지 증명한 것은 아니다. 테스트 코드 주석에도 같은 내용을 적어뒀다.

## 5. P0-4. 토큰 만료된 사람이 로그아웃 못 하던 문제

### 무엇이 문제였나

실제 로그아웃 주소는 이것이다.

```text
POST /api/users/logout
```

그런데 보안 설정 두 곳(`SecurityConfig`, `JwtAuthenticationFilter`)에 적힌 "토큰 없이 통과" 목록에는
**존재하지도 않는 주소**가 들어 있었다.

```text
/api/auth/logout    ← 이런 endpoint는 없음
```

### 왜 문제인가

Controller는 친절하게 만들어져 있었다. "Access Token이 만료됐어도 무시하고 Refresh Token으로 로그아웃해준다."
그런데 **그 코드에 도달을 못 한다.** 앞단의 JWT 필터가 만료 토큰을 보고 먼저 401로 잘라버리기 때문이다.

**"토큰이 만료돼서 로그아웃하려는 상황"** 이야말로 로그아웃이 가장 필요한 순간인데, 정확히 그때 안 됐다.

### 어떻게 고쳤나

**① 목록을 한 곳으로 합쳤다.** (`PublicEndpoints.java`)

애초에 같은 목록을 두 파일이 따로 들고 있어서 어긋난 것이다.
이제 두 곳이 **같은 상수를 참조**하므로 한쪽만 고쳐 어긋나는 일이 구조적으로 불가능하다.

**② 실제 주소로 맞췄다.** `/api/auth/logout` → `/api/users/logout`

**③ `/api/users/**` 전체를 열지 않았다.** 로그아웃 경로 하나만 열었다.

로그아웃을 토큰 없이 허용해도 안전한 이유: **진짜 자격 증명은 body의 refreshToken**이고,
`AuthService.logout()`이 그 토큰의 소유자를 검증한다. 남의 refreshToken 값을 모르면 아무것도 못 한다.

### 어떻게 확인했나

## 6. P1-3. 앨범 목록 N+1 — SQL 202번 → 4번 ⭐ 가장 큰 성능 개선

### 무엇이 문제였나

2026-08-05 성능 측정 결과, **앨범 100개를 보는 데 SQL이 202번** 나갔다.

내역을 뜯어보면 정확히 이렇다.

```text
  1  앨범 목록 조회
100  앨범마다 사진 목록 조회      ← 사진 "개수"를 세려고 사진을 다 불러옴
100  앨범마다 공유 여부 조회      ← existsBy... 를 앨범마다 호출
  1  공유받은 앨범 목록 조회
────
202
```

앨범이 1,000개가 되면 2,002번이 된다. **앨범 수에 정비례해서 늘어나는 구조.**

### 왜 이렇게 됐나 (코드 기준)

```java
albumRepository.findByUserId(userId).stream().map(album -> {
    autoSetThumbnailIfMissing(album);              // ← album.getPhotos() 접근 = SQL 1번
    int photoCount = album.getPhotos().stream()... // ← 사진 개수 세기
    boolean sharedFlag = albumShareRepository
            .existsByAlbumIdAndStatusAndActiveTrue(...);  // ← SQL 1번 더
    ...
})
```

`album.getPhotos()`는 **LAZY** 로딩이다. 평소엔 안 가져오다가 **건드리는 순간** SQL이 나간다.
`.map()` 안에서 앨범마다 건드리니 앨범 수만큼 SQL이 나간 것이다.

### 어떻게 고쳤나 — 대안 비교

| 방법 | 장점 | 단점 | 선택 |
|---|---|---|---|
| **A. EAGER로 변경** | 코드 한 줄 | **모든** 앨범 조회에 사진 전체 로딩 비용이 퍼짐. 상세·수정 등 사진이 필요 없는 곳까지 느려짐 | ❌ |
| **B. Fetch Join** | 한 번에 가져옴 | 1:N을 조인하면 앨범 행이 사진 수만큼 뻥튀기(중복 row). 페이징과 같이 쓰면 Hibernate가 메모리 페이징으로 전락 | ❌ |
| **C. 목록 전용 projection + 일괄 조회** | 필요한 컬럼만, 쿼리 수 고정 | 코드가 조금 늘어남 | ✅ |

**C를 선택한 이유:** 목록 화면이 실제로 필요한 건 **사진 장수와 커버 이미지 URL 뿐**이다.
Photo 엔티티 전체를 메모리에 올릴 이유가 없다.

### 바꾼 구조

쿼리를 **앨범 개수와 무관하게 4개로 고정**했다.

```text
① 소유 앨범 목록                       (photos 컬렉션은 건드리지 않는다)
② 공유받은 앨범 목록                   JOIN FETCH로 Album까지 한 번에
③ 해당 앨범들의 살아있는 사진 행 일괄   ← 100번이 1번으로
④ 공유 중인 앨범 id 일괄               ← 100번이 1번으로
```

③은 필요한 컬럼 4개만 뽑는 전용 projection이다. (`AlbumPhotoRow.java`)

```java
@Query("""
    SELECT new com.nemo.backend.domain.album.dto.AlbumPhotoRow(
               a.id, p.thumbnailUrl, p.imageUrl, p.createdAt)
    FROM Album a JOIN a.photos p
    WHERE a.id IN :albumIds AND p.deleted = false
    """)
```

④는 `exists`를 앨범마다 부르는 대신 **공유 중인 앨범 id 집합을 한 번에** 가져와 메모리에서 조회한다.

```java
Set<Long> sharedWithOthers = new HashSet<>(
        albumShareRepository.findSharedAlbumIds(albumIds, Status.ACCEPTED));
```

**덤으로 고친 것:** 기존 `autoSetThumbnailIfMissing()`은 **목록을 조회하면서 앨범 엔티티를 수정**하고 있었다.
읽기 작업이 데이터를 바꾸는 건 예상 밖의 동작이라, 목록용으로는 엔티티를 건드리지 않는
`resolveCoverUrl()`을 따로 뒀다. **표시 규칙(결과)은 완전히 동일하다.**

### 측정 결과

| 항목 | Before | After |
|---|---:|---:|
| 앨범 100개 조회 SQL 수 | **202** | **4** |
| 앨범 3개 → 30개 SQL 증가 | 비례 증가 | **변화 없음 (둘 다 4)** |

측정 방법은 Hibernate 통계(`statistics.getPrepareStatementCount()`)이며,
`AlbumListQueryCountTest.matchesBaselineScenario()`가 **baseline과 같은 앨범 100개 조건**으로 이 수치를 고정한다.

### 어떻게 확인했나

`AlbumListQueryCountTest.java` — 4개 테스트

- **앨범 3개와 30개의 쿼리 수가 같은지** ← N+1이 다시 들어오면 바로 깨진다
- 앨범 100개 = SQL 4개 (baseline 202와 직접 비교)
- 통계가 꺼져 있어 0 vs 0으로 **공허하게 통과하는 것**을 막는 검증
- 장수·커버·정렬 **결과가 이전과 같은지** (성능 고치다 기능이 바뀌면 안 되므로)
- 삭제된 사진만 있는 앨범은 커버 없음 + 장수 0

### ⚠️ 아직 안 한 것 (정직하게)

- **HTTP avg/p95 재측정을 하지 않았다.** baseline의 k6 조건으로 다시 돌려야 한다.
  → **SQL 수는 측정했고, 응답시간 개선은 아직 수치로 주장하면 안 된다.**
- **메모리 페이징이 남아 있다.** `AlbumController`는 여전히 전체 목록을 만든 뒤 `subList()`로 자른다.
  page 0을 봐도 전체를 메모리에 올린다. 이건 DB 페이징으로 옮기는 별도 작업이다.
  (OWNED/SHARED 목록 병합 + favoriteOnly + 정렬을 함께 설계해야 해서 범위가 크다)
- ③번 쿼리는 **반환 행 수가 사진 수에 비례**한다. 쿼리 수는 고정이지만 행 수는 그렇지 않다.
  다만 Photo 엔티티 전체가 아니라 컬럼 4개만 가져오므로 이전보다 훨씬 가볍다.

## 7. P1-4. 타임라인이 전체 사진을 읽던 문제

### 무엇이 문제였나

```java
// 2026년 8월 타임라인을 보려는데
List<Photo> photos = photoRepository.findByUserIdAndDeletedIsFalseOrderByTakenAtDesc(userId);
                                                              // ↑ 사용자의 사진 "전부"
for (Photo photo : photos) {
    if (year != null && date.getYear() != year) continue;      // ← Java에서 버림
    if (month != null && date.getMonthValue() != month) continue;
}
```

**한 달치를 보려고 몇 년치를 다 읽어와서 Java에서 버리고 있었다.**

### 왜 문제인가

지금 1,000장 규모에서는 체감되지 않는다. 그래서 **"심각한 장애"로 부풀리지 않는다.**
문제는 구조다. 사진이 10,000장이 되면 8월 화면 한 번에 10,000개 객체를 JVM에 올린다.
사용자가 쓸수록 느려지는 방향의 구조다.

### 어떻게 고쳤나

DB에서 기간을 자른다.

```java
@Query("""
    SELECT p FROM Photo p
    WHERE p.userId = :userId
      AND p.deleted = false
      AND COALESCE(p.takenAt, p.createdAt) >= :start
      AND COALESCE(p.takenAt, p.createdAt) < :end
    ORDER BY p.takenAt DESC
    """)
```

**여기서 조용히 틀리기 쉬운 지점 3가지를 짚었다.**

**① `COALESCE(takenAt, createdAt)` — 이게 없으면 사진이 사라진다**

기존 `resolveDate()`는 "촬영일이 없으면 업로드일을 쓴다"였다.
DB 쿼리에서 `takenAt`만 봤다면 **촬영일 없는 사진이 타임라인에서 조용히 증발**했을 것이다.
기존 의미를 그대로 DB로 옮겼다.

**② 반열림 구간 `[start, end)`**

`>= 8월 1일 00:00` 그리고 `< 9월 1일 00:00`.
`<= 8월 31일`로 했다면 **8월 31일 23시 59분 사진이 빠진다.** 흔한 실수다.

**③ 12월 → 다음 해 1월 경계**

`month + 1`로 계산했다면 12월에서 **13월**이 되어 터진다.
`LocalDateTime.plusMonths(1)`이 알아서 다음 해 1월로 넘긴다.

**연도 없이 월만 지정한 경우**(모든 해의 N월)는 하나의 연속 구간으로 표현할 수 없어
기존 방식(전체 조회 + Java 필터)을 그대로 뒀다. 억지로 바꾸지 않았다.

### 어떻게 확인했나

`TimelinePeriodQueryTest.java` — 8개 테스트. **결과가 이전과 같은지(동등성)** 를 확인하는 게 목적이다.

| 테스트 | 확인 내용 |
|---|---|
| 12월 / 다음 해 1월 | 서로 섞이지 않음 |
| 월 시작 00:00 / 월말 23:59:59 / 다음 달 00:00 | 반열림 구간이 정확한지 |
| 윤년 2월 29일 | 누락되지 않음 (2028년) |
| **촬영일 없는 사진** | 업로드일 기준으로 잡힘 (증발 안 함) |
| 삭제된 사진 | 제외됨 |
| 연도만 지정 / 아무것도 지정 안 함 | 각각 1년치 / 전체 |
| 타임랩스 | 그 달만, 28일 전부 반환 |

### ⚠️ 아직 안 한 것

- **인덱스는 만들지 않았다.** 개선 문서 원칙대로 **`EXPLAIN ANALYZE`로 병목을 확인한 뒤** 결정한다.
  지금 데이터 크기에서는 실행계획을 봐도 의미 있는 판단이 안 나온다.
  `COALESCE`를 쓰므로 단순 컬럼 인덱스는 안 먹을 수 있고, **표현식 인덱스**를 검토해야 한다는 점만 기록해둔다.
- Before/After 응답시간 수치 없음. (P1-3과 동일한 이유)

## 9. 면접에서 물어볼 만한 것 & 준비된 답

**Q. N+1을 어떻게 발견했나?**
> 성능 측정에서 앨범 100개 조회에 SQL 202개가 나오는 걸 확인했다. 내역을 뜯어보니
> 목록 1 + 앨범당 사진 조회 100 + 앨범당 공유여부 조회 100 + 공유목록 1이었다.
> 코드에서는 `.map()` 안에서 LAZY 컬렉션을 건드리는 지점과 `existsBy`를 반복 호출하는 지점이었다.

**Q. Fetch Join을 안 쓴 이유는?**
> 1:N 조인은 앨범 행이 사진 수만큼 중복되고, 페이징과 함께 쓰면 Hibernate가 메모리 페이징으로 떨어진다.
> 목록 화면이 실제로 필요한 건 장수와 커버 URL뿐이라, 필요한 컬럼만 뽑는 전용 projection이 더 명시적이었다.

**Q. 개선을 어떻게 증명하나?**
> 쿼리 수를 세는 테스트로 고정했다. 단순히 총량이 아니라 **앨범 3개일 때와 30개일 때가 같은지**를 검증한다.
> N+1이 다시 들어오면 이 테스트가 깨진다. 다만 HTTP 응답시간 재측정은 아직 안 해서, 지금은 SQL 수만 주장한다.

**Q. `readOnly = true`가 왜 위험했나?**
> flush 모드가 MANUAL이 되어 변경이 DB에 반영되지 않는다. **에러 없이 조용히 사라진다.**
> 고치는 과정에서 두 번째 문제도 찾았는데, 삭제 후 예외를 던지면 롤백이 삭제까지 되돌린다는 점이었다.
> "요청은 실패시키되 정리는 남긴다"는 두 개의 독립적 작업이라 `REQUIRES_NEW`로 분리했다.

**Q. 권한 검사가 이미 있었는데 왜 뚫렸나?**
> 있던 건 "이 앨범을 수정할 수 있는가"였다. "이 사진을 쓸 수 있는가"는 다른 질문인데 아무도 묻지 않았다.
> 두 검사를 테스트 이름으로도 분리해서 다시 헷갈리지 않게 했다.

## 11. 이 작업에서 지킨 원칙

- 문제 하나당 **실패를 재현하는 테스트를 먼저** 두고 고쳤다.
