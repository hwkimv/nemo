# 핵심 조회 API 성능 Baseline

**상태:** Verified

**측정일:** 2026-08-05

**대상:** NEMO 현재 구현의 Before 성능

## 1. 측정 목적

성능 변경을 적용하기 전에 앨범, 사진, 타임라인 조회의 Query 수와 HTTP 응답시간을 재현 가능한 조건에서 기록했다. 이 문서의 값은 로컬 전용 PostgreSQL에서 관찰한 Baseline이며 운영 성능을 뜻하지 않는다.

## 2. 아키텍처와 JPA 관계

```text
HTTP + JWT
→ Spring MVC Controller
→ Service / Transaction
→ Spring Data JPA Repository
→ PostgreSQL 17
```

- `Album`은 소유자 `User`와 N:1 LAZY, `Photo`와 N:M LAZY 관계다.
- `AlbumShare`와 `AlbumFavorite`은 각각 `Album`, `User`를 LAZY로 참조한다.
- `Photo`는 Entity 관계 대신 `userId` 컬럼 값을 보관한다.
- 타임라인 서비스는 별도 `Timeline` 조회가 아니라 `PhotoRepository` 결과를 사용한다.

## 3. 데이터와 실행 조건

| 항목 | 조건 |
|---|---:|
| DB | 전용 Docker PostgreSQL 17.10, `nemo_benchmark` |
| 측정 사용자 | ID 1, `benchmark-target@nemo.local` |
| 전체 사용자 | 100명 |
| 소유 앨범 | 100개 |
| 사진 | 1,000개, 앨범당 10개 |
| 공유 / 즐겨찾기 | 각 20개 |
| HTTP 부하 | API별 1 VU, 30회, 세 API 시작 시간 분리 |
| 반복 횟수 | 서비스 Query 3회, k6 3회 |

Seed는 실행 전 DB 이름을 검사하며 `nemo_benchmark`가 아니면 중단한다. 운영 Supabase, 운영 S3, 실제 이미지 전송은 사용하지 않았다.

## 4. API 흐름

### 앨범 목록

`GET /api/albums?ownership=OWNED&page=0&size=10`

```text
AlbumController.getAlbums
→ AlbumService.getAlbums
→ AlbumRepository.findByUserId
→ 각 Album.photos와 공유 여부 접근
→ 메모리 정렬·페이지 분할
```

### 사진 목록

`GET /api/photos?page=0&size=20&sort=takenAt,desc`

```text
PhotoController.list
→ PhotoServiceImpl.list
→ PhotoRepository.findForList(Pageable)
→ Page<PhotoResponseDto>
```

### 타임라인

`GET /api/timeline?year=2025&month=1`

```text
TimelineController.getTimeline
→ TimelineServiceImpl.getTimeline
→ 사용자의 전체 Photo 조회
→ Java에서 연·월 필터와 날짜별 그룹화
```

## 5. 서비스 Query 수 3회

Hibernate Statistics의 prepared statement 수를 서비스 직접 호출 전후로 측정했다. 인증 Query와 HTTP 직렬화 비용은 포함하지 않는다.

| API | 1회차 | 2회차 | 3회차 | 반환 행/항목 | 서비스 시간 평균 |
|---|---:|---:|---:|---:|---:|
| 앨범 | 202 | 202 | 202 | 100 | 435.3ms |
| 사진 | 2 | 2 | 2 | 20 | 114.3ms |
| 타임라인 | 1 | 1 | 1 | 31일 그룹 | 906.0ms |

앨범 조회는 한 번의 서비스 호출에 202개 statement가 반복되어 N+1 후보가 실제 측정으로 확인됐다. 타임라인은 Query 수는 1개지만 1,000개 사진을 모두 읽고 JVM에서 기간을 필터링한다.

## 6. k6 HTTP 측정 3회

아래 평균과 p95는 setup 토큰 요청을 제외하고 각 API 태그에 속한 30개 요청만 집계한 값이다. 세 실행 모두 전체 91개 check가 통과했고 `http_req_failed`는 0이었다.

| API | 지표 | 1회차 | 2회차 | 3회차 | 3회 산술평균 |
|---|---|---:|---:|---:|---:|
| 앨범 | 평균 | 136.12ms | 114.23ms | 113.29ms | 121.21ms |
| 앨범 | p95 | 192.90ms | 120.63ms | 120.56ms | 144.70ms |
| 사진 | 평균 | 17.63ms | 14.93ms | 12.82ms | 15.13ms |
| 사진 | p95 | 22.23ms | 23.93ms | 15.59ms | 20.58ms |
| 타임라인 | 평균 | 18.67ms | 18.40ms | 17.85ms | 18.31ms |
| 타임라인 | p95 | 23.34ms | 20.87ms | 19.93ms | 21.38ms |

낮은 동시성의 로컬 측정이므로 최대 처리량이나 운영 지연시간을 나타내지는 않는다. 첫 앨범 실행의 최대값 558.46ms가 1회차 p95 편차에 영향을 줬다.

## 7. PostgreSQL 실행 계획

사진 첫 페이지 Query와 타임라인 전체 사진 Query 모두 `user_id = 1 AND deleted = false` 조건에서 `Seq Scan` 후 `taken_at DESC` 정렬을 사용했다.

| Query | 읽은 행 | 정렬 | 실행시간 |
|---|---:|---|---:|
| 사진 `LIMIT 20` | 1,000행 | top-N heapsort, 35kB | 0.319ms |
| 타임라인용 전체 사진 | 1,000행 | quicksort, 204kB | 0.478ms |

현재 데이터는 1,000행으로 작아 DB 실행시간 자체는 짧다. 이 결과만으로 인덱스 효과를 단정할 수 없고, 더 큰 데이터 규모에서 별도 비교가 필요하다.

## 8. 병목 후보

1. 앨범 목록: 100개 앨범 조회에 202개 statement가 발생하는 LAZY 연관 접근과 앨범별 공유 여부 조회.
2. 앨범 목록: DB Pagination이 아니라 전체 결과 생성 후 메모리에서 정렬·분할하는 구조.
3. 타임라인: 1,000개 사진 전체 전송 후 JVM에서 연·월을 필터링하는 구조.
4. 사진·타임라인 Query: 현재 실행 계획의 순차 스캔과 정렬. 데이터 확대 후 복합 인덱스 비교 필요.

후속 작업의 우선순위는 Query 수와 HTTP 지연이 함께 큰 앨범 목록으로 잡을 수 있다.

## 9. 비범위

- 인덱스 추가와 전후 수치 비교

## 10. 재현 순서

```bash
docker compose --profile benchmark up -d postgres-benchmark
docker compose exec -T postgres-benchmark psql -U nemo_benchmark -d nemo_benchmark < tools/performance/sql/seed.sql
docker compose exec -T postgres-benchmark psql -U nemo_benchmark -d nemo_benchmark < tools/performance/sql/verify-seed.sql

cd backend
SPRING_PROFILES_ACTIVE=benchmark ./gradlew performanceBaseline --rerun-tasks --no-daemon
cd ..

k6 run -e BASE_URL=http://localhost:8080 tools/performance/k6/baseline.js
docker compose exec -T postgres-benchmark psql -U nemo_benchmark -d nemo_benchmark < tools/performance/sql/explain.sql
```

HTTP 측정 전에는 `benchmark` profile 서버와 LocalStack을 로컬에서 실행해야 한다. Naver 환경변수는 지도 API를 호출하지 않는 로컬 더미 값을 사용한다.

Raw 결과는 `build/performance-baseline/`에 있으며 실행 환경 산출물이므로 Git에는 포함하지 않는다.
