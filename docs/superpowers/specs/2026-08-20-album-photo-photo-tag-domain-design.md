# AlbumPhoto·PhotoTag 도메인 구현 설계

## 1. 목적

현재 `Album`과 `Photo`는 JPA `@ManyToMany`로 연결돼 있어 관계 자체에 사진 순서를 저장할 수 없다. 사진 태그도 문서에는 `PhotoTag`로 설계돼 있지만 실제 코드와 API가 없다.

이번 변경의 목적은 다음 두 가지다.

1. 기존 `album_photos` 데이터를 유지하면서 관계를 `AlbumPhoto` 엔티티로 승격하고, 앨범 안 사진 순서를 영속화한다.
2. 사진 소유자가 수락된 친구를 사진 위치에 태그하고, 접근 가능한 사용자가 조회하며, 소유자와 태그된 사용자가 삭제할 수 있는 `PhotoTag` 기능을 구현한다.

이 변경은 이력서 문장을 맞추기 위한 빈 엔티티 추가가 아니다. 기존 앨범 순서 문제와 기획 문서의 친구 태그 사용 흐름을 실제 API와 테스트로 완성하는 작업이다.

- PostgreSQL Flyway 마이그레이션
- H2 단위·통합 테스트와 PostgreSQL 마이그레이션 스모크 테스트

## 3. 선택한 데이터 모델

### 3.1 AlbumPhoto

기존 테이블명 `album_photos`와 기존 행을 유지한다. 새 테이블로 복사하지 않는다.

```text
album_photos
- album_id   BIGINT  PK, FK -> album.id
- photo_id   BIGINT  PK, FK -> photos.id
- sequence   INTEGER NOT NULL
- UNIQUE(album_id, sequence)
```

`AlbumPhotoId(albumId, photoId)`를 `@Embeddable` 복합키로 사용한다. `AlbumPhoto`는 `@EmbeddedId`와 `@MapsId`로 `Album`, `Photo`를 연결한다. 별도 대리키를 추가하지 않는 이유는 기존 조인 테이블 구조와 데이터를 가장 적게 바꾸기 위해서다.

`Album`은 `List<AlbumPhoto>`를 `@OneToMany(mappedBy = "album", cascade = ALL, orphanRemoval = true)`로 가진다. 서비스가 계산된 `List<Photo>`를 직접 수정하지 않도록 다음 도메인 메서드를 제공한다.

- `addPhoto(Photo photo, int sequence)`
- `containsPhoto(Long photoId)`
- `removePhotos(Set<Long> photoIds)`
- `compactSequences()`
- `orderedAlivePhotos()`

순서는 0부터 시작한다.

- 앨범 생성: 요청 `photoIdList`의 순서를 그대로 저장한다.
- 사진 추가: 현재 최대 sequence 다음에 요청 순서대로 추가한다.
- 사진 삭제: 삭제 후 남은 연결의 sequence를 0부터 연속 값으로 압축한다.
- 기존 데이터 이전: 과거 순서 정보가 없으므로 앨범별 `photo_id ASC` 순으로 결정적인 초기 sequence를 부여한다. 이 값은 과거 사용자 순서를 복원한 값이 아니다.

### 3.2 PhotoTag

```text
photo_tag
- id               BIGINT GENERATED BY DEFAULT AS IDENTITY PK
- photo_id         BIGINT NOT NULL FK -> photos.id
- tagged_user_id   BIGINT NOT NULL FK -> users.id
- position_x       DOUBLE PRECISION NOT NULL
- position_y       DOUBLE PRECISION NOT NULL
- created_at       TIMESTAMP NOT NULL
- UNIQUE(photo_id, tagged_user_id)
```

`positionX`, `positionY`는 이미지 가로·세로에 대한 비율이며 각각 `0.0` 이상 `1.0` 이하만 허용한다.

한 사진에 같은 사용자를 두 번 태그할 수 없다. 좌표 변경은 이번 범위에서 지원하지 않으며, 기존 태그를 삭제한 뒤 다시 추가한다.

## 4. API

### 4.1 태그 추가

```http
POST /api/photos/{photoId}/tags
Authorization: Bearer <token>
Content-Type: application/json

{
  "taggedUserId": 2,
  "positionX": 0.42,
  "positionY": 0.35
}
```

성공 시 `201 Created`와 생성된 태그를 반환한다.

검증 순서:

1. 요청자가 사진 소유자인지 확인한다.
2. 사진이 삭제되지 않았는지 확인한다.
3. 태그 대상 사용자가 존재하는지 확인한다.
4. 요청자와 대상 사이에 `ACCEPTED` 친구 관계가 한 방향 이상 존재하는지 확인한다.
5. 좌표 범위를 확인한다.
6. 같은 사진·사용자 태그가 이미 있으면 `409 Conflict`를 반환한다.

본인 태그는 허용하지 않는다. 본인은 사진 소유자로 이미 식별되며 친구 태그 통계의 의미와도 맞지 않는다.

### 4.2 태그 조회

```http
GET /api/photos/{photoId}/tags
Authorization: Bearer <token>
```

사진 소유자이거나, 수락된 공유 앨범을 통해 해당 사진에 접근 가능한 사용자만 조회할 수 있다. 응답은 `tagId`, `taggedUserId`, `nickname`, `positionX`, `positionY`, `createdAt`을 포함한다.

### 4.3 태그 삭제

```http
DELETE /api/photos/{photoId}/tags/{tagId}
Authorization: Bearer <token>
```

사진 소유자는 사진의 모든 태그를 삭제할 수 있다. 태그된 사용자는 자신의 태그를 직접 삭제할 수 있다. 그 외 사용자는 `403 Forbidden`을 받는다. 성공 시 `204 No Content`를 반환한다.

## 5. 기존 앨범 API 호환성

외부 요청과 응답 형식은 바꾸지 않는다.

- `POST /api/albums`
- `POST /api/albums/{albumId}/photos`
- `DELETE /api/albums/{albumId}/photos`
- `GET /api/albums/{albumId}`
- `GET /api/albums/{albumId}/download-urls`
- 앨범 썸네일·공유·사진 다운로드 권한 흐름

기존 코드의 `album.getPhotos()` 의존은 `AlbumPhoto` 도메인 메서드 또는 `AlbumPhotoRepository`의 존재·목록 쿼리로 교체한다. `PhotoServiceImpl`, `PhotoController`, `AlbumShareService`, `AuthService`에 남은 직접 접근도 함께 제거한다.

앨범 다운로드 응답의 `sequence`는 더 이상 조회 시 임시로 붙인 번호가 아니라 DB에 저장된 값을 사용한다.

## 6. 목록 쿼리 성능

기존 목록 Projection Query는 다음 관계로 변경한다.

```jpql
FROM Album a
JOIN a.albumPhotos ap
JOIN ap.photo p
```

앨범 목록 100개 기준 SQL 수 목표는 기존과 동일한 4개다.

1. 소유 앨범 페이지
2. 공유받은 앨범 정보
3. 대상 앨범의 살아있는 사진 Projection
4. 공유 중 앨범 ID

`AlbumListQueryCountTest`를 새 모델로 고치되 기대값 4를 유지한다. 쿼리 수가 늘면 구현을 완료한 것으로 보지 않는다.

## 7. 오류 코드

다음 도메인 오류를 추가한다.

- `PHOTO_TAG_ALREADY_EXISTS` — 409
- `PHOTO_TAG_NOT_FOUND` — 404
- `PHOTO_TAG_FORBIDDEN` — 403
- `PHOTO_TAG_SELF_NOT_ALLOWED` — 400
- `PHOTO_TAG_TARGET_NOT_FRIEND` — 403
- `PHOTO_TAG_POSITION_INVALID` — 400

사진 존재 여부를 제3자가 탐색하지 못하도록 사진 소유권·접근 권한 검증을 태그 대상과 중복 검증보다 먼저 수행한다.

## 8. 데이터베이스 마이그레이션

운영 프로필은 `ddl-auto: validate`이므로 Hibernate가 테이블을 만들 것으로 기대하지 않는다. Flyway를 운영 프로필에 활성화한다.

- 기존 비어 있지 않은 스키마는 baseline version `0`으로 등록한다.
- `V1__album_photo_and_photo_tag.sql`에서 `album_photos.sequence` 추가·백필·제약과 `photo_tag` 생성을 수행한다.
- 기존 `album_photos`에 같은 `(album_id, photo_id)` 행이 중복돼 있으면 임의로 삭제하지 않고 명확한 오류로 마이그레이션을 중단한다. 데이터 정리는 별도 승인 없이 수행하지 않는다.
- 개발 H2와 일반 테스트는 기존 Hibernate `ddl-auto: update/create-drop` 흐름을 유지하고 Flyway를 비활성화한다.
- PostgreSQL 마이그레이션 테스트는 기존 형태의 `album_photos` 행을 먼저 만든 뒤 V1을 실행해 행 보존과 sequence 백필을 확인한다.

마이그레이션은 기존 데이터의 의미를 확대하지 않는다. 과거 사진 순서가 없었다는 한계를 README와 사례 문서에 기록한다.

## 9. 테스트 전략

모든 프로덕션 변경은 실패하는 테스트를 먼저 작성한 뒤 최소 구현으로 통과시킨다.

### AlbumPhoto

- 기존 앨범 사진이 `AlbumPhoto`로 저장된다.
- 생성 요청 순서가 sequence로 보존된다.
- 추가 사진이 마지막 sequence 뒤에 요청 순서대로 붙는다.
- 중복 사진은 추가되지 않는다.
- 삭제 뒤 sequence가 0부터 압축된다.
- 상세와 다운로드가 sequence 순서로 반환된다.
- 썸네일·공유 권한·회원 탈퇴 시 연결 행이 올바르게 처리된다.
- 앨범 100개 목록 SQL 수가 4개다.

### PhotoTag

- 사진 소유자가 수락된 친구를 태그할 수 있다.
- 남의 사진, 삭제된 사진, 친구가 아닌 사용자, 본인, 범위 밖 좌표를 거부한다.
- 같은 사진·사용자 중복을 거부한다.
- 사진 접근 사용자는 태그를 조회할 수 있다.
- 사진 소유자와 태그된 사용자는 삭제할 수 있다.
- 다른 사용자는 삭제할 수 없다.

### 전체 검증

- `./gradlew test --no-daemon`
- PostgreSQL Flyway 마이그레이션 스모크 테스트
- `git diff --check`
- 기존 공개 API 응답 필드 비교

## 10. 완료 기준과 증거 경계

다음 조건을 모두 충족해야 코드 구현 완료로 본다.

1. 새 기능 테스트와 기존 전체 테스트가 통과한다.
2. PostgreSQL 마이그레이션이 기존 연결 행을 보존한다.
3. 앨범 목록 SQL 4개 회귀 테스트가 통과한다.
4. 문서 설명과 현재 코드가 일치한다.
5. 팀 저장소와 기존 dirty checkout에는 변경이 없다.

로컬·테스트 구현은 운영 배포를 뜻하지 않는다. 실제 Supabase 적용과 사용자 데이터 전환은 별도 실행 증거가 생기기 전까지 `미배포`로 기록한다.
